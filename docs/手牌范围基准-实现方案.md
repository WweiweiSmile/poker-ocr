# 手牌范围基准：实现方案

> 对应文档：[`docs/手牌范围基准-现状与缺口.md`](./手牌范围基准-现状与缺口.md)
> 目标不变：**hand vs ranges** —— 给定我的手牌、实际牌面、池里每个对手的范围，
> 回答“我现在领先什么 / 落后什么 / 打到河牌有多少权益”。
> 不是 range vs range 的整体优势，不是 3–5 人 GTO，也不是 solver 的尺度/单手 EV。

---

## 0. 结论：好实现，但难点不在代码

**计算层是好实现的；范围数据才是工作量。**

- 计算层：现有的 `coach.evaluate`（实测约 4.5µs/次）、`preflop_ranges.expand`、
  `HandSnapshot` 里的位置/动作/在局信息已经够用。原型实测：
  - 3 人池、2000 次 MC（含逐对手 `behind`、联合 `behind_any`、翻牌后发 2 张转河）约 **80ms**；
  - 逐对手精确枚举 `behind_i` 约 **5ms**（3 个范围合计约 1,400 个去重后组合）；
  - 4 人池 1500 次约 **80ms**。加缓存后同一决策点应 <1ms。
- 数据层：冷跟、按开池位置的 BB 防守、3-bet 跟注这三张表是瓶颈。
  按“程序生成 + 人工复核”做，**整体 2–3 天**能到可用，**5–7 天**能到可信。
- 文档方向是对的：不做 184、不做 3–5 人 GTO、不把 solver 表当答案。但有 4 个口径
  必须先修正，否则算得越准越误导：

1. **范围是描述性的，不是规范性的。**
   默认范围应贴“这个池子实际会拿什么”，不是“他应该拿什么”。
   文档里“BB 44% 对 UTG 太宽、底部 -EV”是**策略批评**，不是**范围建模错误**：
   如果对手真的用 44% 跟，那 44% 就是正确范围（虽然他自己 -EV）。
   更要紧的是：这个“-EV”结论**没有算前注**。本桌 0.5BB ante、9 人桌，
   6BB open 下 BB 跟 5BB 进约 17BB 的池，**原始赔率约 29%**，不是无前注的 41.7%；
   按 raw equity 看，44% 的宽度并不自动是 -EV（见 §3.3 的粗算）。
   所以“44% 太宽”可以作为一个待验证的策略假设，不能当既定事实写进范围表。

2. **必须按 6BB open + 0.5BB ante 校准。**
   本桌翻前最低加注 6BB（`poker_ocr/advice.py:144`），不能直接抄 2.5BB 的 GTO 图表；
   前注又会把 BB 的赔率从 41.7% 拉到约 29%。同一手牌在 2.5BB 无前注和 6BB 有前注下
   是两套范围，必须按本桌结构重新生成。

3. **文档漏了 limped / bomb pot。**
   现场 3–5 人池大量是 limped（`snap.preflop_shapes` 已有 `limped`），bomb pot 也有
   `snap.bomb_pot`。这两类没有 RFI 范围可用，必须单独建 `LIMP_*` / `BOMB`，或者
   明确降级为“random lower bound”；否则最常见的池型反而没有基准。

4. **画像不能只做文本偏移。**
   `opponent_profile.OpponentRead` 已经有 `vpip / pfr / n / archetype / gate`，
   应该变成范围宽度的数值修正（带样本收缩），否则默认范围与画像会互相矛盾。

还有一个文档没展开、但实现时必须处理的问题：**“现在领先”和“权益”不是一回事**。
完整口径有三个量，v1 至少要把前两个分开，第三个是 P1 的解释项：

- `behind_now`：按**当前成手牌**排名，他的范围里现在有多少比我大；
- `draw_share`：他范围里有多少强听牌（现在不领先，但有权益）；
- `equity`：打到河牌的权益（含听牌、含后续发牌）。

只用 `behind_now`，会把“TPTK vs 花听”说成大幅领先；只用 `equity`，又说不清
“现在是不是已经落后”。v1 必须同时渲染 `behind_now` 和 `equity`，
`draw_share` 用来解释两者为什么差这么多（P1）。原型里这组对比很直观：

| 我的手牌 / 牌面 | 现在至少一家领先 | 打到河牌权益 |
|---|---|---|
| `AhKd` on `Ks7d2c`（TPTK，3-way） | 约 14% | 约 60% |
| `AhQh` on `Kh7h2c`（坚果花听，3-way） | 约 87% | 约 44% |

花听现在“大幅落后”，但有 44% 权益；TPTK 现在“大幅领先”，权益却只有 60%
（多人池 + 听牌 + 后续发牌）。这两个数必须一起出现，且标签不能混。

## 2. 总体架构

```text
HandSnapshot
  │
  ├─ field_ranges.resolve(snap) ──► 每个在局对手的范围 + 动作 mode + 宽度
  │        │
  │        ├─ ranges.get(id) ──► 169 键 × 权重 ──► 1,326 组合（翻前先验）
  │        │
  │        └─ board_range.build(board, mode, prior) ──► 实时牌面关联范围
  │                 （见 docs/实时牌面范围-设计.md；纯牌面 / 先验×牌面）
  │
  ├─ hand_vs_ranges.compute(hero, board, field)
  │        ├─ 逐对手 behind_i / tie_i / ahead_i（精确、加权、去重牌）
  │        ├─ 逐对手 beaten_by 分组（范围加权）
  │        ├─ 联合 behind_any（MC，整组拒绝重抽）
  │        ├─ equity vs field（MC，发完转河）
  │        └─ draw_share（P1，可选）
  │
  └─ Situation.hand_ranges ──► “## Hand vs ranges” 事实块
                                      │
                                      └─ _LEAN_SYSTEM 优先级/口径规则

board_equity（P1 重构）──► 复用同一个 field_ranges / ranges，算 range vs range 背景
```

> 两条范围来源可以并存：**翻前先验**回答“他实际可能有什么”，
> **实时牌面范围**回答“在有关联的牌里我算强还是弱”。
> 后者按对手当前街动作选 `check / call / bet / raise` 模式，
> 设计见 [`docs/实时牌面范围-设计.md`](./实时牌面范围-设计.md)。

原则：

- **单一数据源**：`RFI_*` 从 `CHART_ADDITIONS` 生成；`spots.json` 的 `ip_range`
  改为生成或删除；范围表不手写两份。
- **描述性先验 + 显式画像修正**：默认范围贴 app 池；画像只做可解释的宽度缩放，
  且样本不足时不动。
- **fail open**：任何一步缺数据都返回 `None` + 一条 `Data gaps`，绝不用 BB 范围
  去冒充其他位置（当前 `board_equity` 就是这么干的）。
- **确定性**：采样种子由 `(street, board, hero, range_ids)` 派生，同一决策点每次
  输出一致；缓存有上限。

## 3. 范围数据

### 3.1 数据模型

不要直接写 1,326 个组合。用 **169 键 + 频率**，在加载时展开：

```python
# poker_ocr/ranges.py
Card = tuple[int, str]                 # (0..12, 's'|'h'|'d'|'c')，和 coach 一致
Combo = tuple[Card, Card]

@dataclass(frozen=True)
class Range:
    id: str
    version: int
    weights: Mapping[str, float]       # 169 键 -> 0..1（频率）
    ordered_keys: tuple[str, ...]      # 生成时的入选顺序，供画像缩放用（P2）
    note: str = ""
    source: str = ""

    def combos(self) -> tuple[Combo, ...]: ...      # 展开、缓存
    def width_pct(self) -> float: ...               # 组合加权 / 1326
```

JSON 形状（`poker_ocr/range_data/ranges.json` 或按家族拆文件）：

```json
{
  "version": 1,
  "meta": {
    "open_size_bb": 6,
    "effective_stack_bb": 100,
    "ante_bb": 0.5,
    "pool": "app-loose-passive",
    "source": "generated from RFI + equity/playability calibration",
    "updated": "2026-10-28"
  },
  "ranges": {
    "BB_DEF_vs_BTN": {
      "tokens": ["22+", "A2s+", "K5s+", "Q7s+", "J8s+", "T8s+", "98s", "87s",
                 "A2o+", "K9o+", "Q9o+", "J9o+", "T9o"],
      "mixed": {"K4s": 0.5, "Q6s": 0.5, "K8o": 0.5},
      "note": "6BB open, 100BB, app pool; width ~40%",
      "source": "gen_ranges.py --check"
    }
  }
}
```

规则：

- 对子 6 个组合、同花 4 个、非同花 12 个；宽度 = Σ(权重 × 组合数) / 1326。
- `mixed` 只能出现 <1 的频率；同一个键不能既在 `tokens` 里又在 `mixed` 里
  （否则加载时报错，测试里必须拦住）。
- 展开复用/扩展现有 `expand()`，新增 `A5s:0.5` 或 `mixed` 语法即可；不要另写一套解析。
- 空范围、负权重、非法键：加载时 `ValueError`；运行时 `get()` 失败返回 `None`（fail open）。

### 3.2 范围清单（v1 够用即可）

| 家族 | ID 形态 | 数量 | 说明 |
|---|---|---|---|
| 开池 | `RFI_<pos>` | 7 | 从 `CHART_ADDITIONS` 生成，不落 JSON |
| BB 防守 | `BB_DEF_vs_<opener>` | 7 | 按开池位置；不再 7 个 spot 共用 |
| 冷跟 | `COLD_CALL_<IP/OOP>_vs_<EP/MP/LP>` | 6 | 位置桶，避免 20+ 张表 |
| 溜入 | `LIMP_<EP/MP/LP>` | 3 | limped pot 的溜入者/跟注者 |
| BB 过牌 | `BB_CHECK` | 1 | limped pot 的 BB（几乎任意两张）；没有表就用 random |
| 炸弹池 | `BOMB` | 1 | 或直接降级为 random |
| 3-bet | `3BET_vs_<EP/MP/LP>` | 3 | 价值 + 诈唬粗表 |
| 3-bet 跟注 | `3BET_CALL_vs_<EP/MP/LP>` | 3 | 面对 3-bet 的继续范围 |
| （P2）4-bet | `4BET` / `4BET_CALL` | 2 | 低频，v1 可返回 None |

**不要**一上来做 `COLD_CALL_<caller>_vs_<opener>` 的 42 张全矩阵。位置桶 + 后续覆盖
足够回答“他大概是什么范围”，而且人可复核。

### 3.3 数据从哪来：生成，不手抄

这是整个方案的关键。建议 `tools/gen_ranges.py`：

1. **读入**：现有 `RFI[pos]`、实际开注尺寸、前注、有效筹码。
2. **逐手牌算 equity**：对 169 个键，按去重牌从开池方范围抽对手手牌，
   随机发 5 张公共牌，算 raw equity（固定 seed，2,000–4,000 次/手）。
3. **算可玩性分**（不是纯 equity）：对子、同花、连张/隔张、双高张、A 踢脚；
   对“被统治的非同花 A/K/Q”（A2o–A9o、K2o–K8o 等）扣分，避免生成
   “equity 勉强够但翻后没法玩”的范围。
4. **分层选择**：
   - 3-bet 价值：equity 顶部 + 阻断牌；
   - 3-bet 诈唬：同花轮子 A、KQs/KJs（对晚位），按本桌“3-bet 很窄”的桌风可关掉；
   - 跟注：**先按目标宽度选，raw equity 和 playability 都是特征，不做单一阈值**；
     因为前注下 raw equity 门槛很低（见下），单用 equity 会选得过宽；
   - 剩下的弃牌。
5. **输出**：JSON + 13×13 文本矩阵 + 指标（宽度、平均 equity、最底部手牌）；
   `--check` 模式重生成并与仓库文件比对，测试里跑。
6. **人工复核**：看 13×13 图和底部手牌是否荒唐（例如“UTG 冷跟 72o”），
   调阈值而不是逐手改表。

#### 6BB + 0.5BB ante 的赔率口径（为什么不能抄 2.5BB 图）

同是 6BB open，前注的有无会把 BB 的价格差出 12 个百分点：

| 口径 | BB 跟注 / 最终底池 | 原始赔率 |
|---|---|---|
| 无前注、9 人桌、SB 弃牌 | 5 / 12 | 41.7% |
| 本桌 0.5BB ante、9 人桌 | 5 / 17 | **29.4%** |

前注把赔率拉到约 29% 后，**raw equity 几乎不再是筛选器**：我按“对 UTG RFI 的
raw equity”粗算（1,200 次/手，仅 sanity check），169 键里有 139 个键 / 966 个组合
（72.9%）的 raw equity ≥29%。连 `72o` 都有约 23.5%、`Q4s` 约 30.4%、
`K2s` 约 34.9%。所以：

- 不能再用“raw equity ≥ 赔率”生成跟注范围，否则会得到 70%+ 的宽度；
- 真正的约束是**实现权益**（OOP、被统治、多人池、反向隐含赔率）和可玩性；
- 文档里的“40% 门槛”是一个**策略/实现权益门槛**，不是本桌赔率；
  用它可以生成更紧的表，但要把口径写清楚，不能拿它当“赔率说这是 -EV”。
- 无前注 + 40% 门槛的粗算会得到约 13% 的 BB 防守宽度；那是另一种口径，
  不能直接搬到本桌。

本方案默认选**描述性**先验（贴池子实际会拿什么），因为 `hand vs ranges` 问的是
“他手里可能是什么”；同时保留一个更紧的 `TAG` 先验，给未知紧手回退。

#### 目标宽度（起始值，必须用数据校准）

| 范围 | vs EP | vs MP | vs LP | 备注 |
|---|---|---|---|---|
| BB 防守（松弱池先验） | 30–40% | 35–45% | 40–55% | 6BB + ante；当前静态 44% 不算离谱，问题是“7 个 spot 共用一套” |
| BB 防守（紧手先验） | 20–28% | 25–35% | 32–45% | 给未知/TAG 对手；不是本桌默认 |
| 冷跟 IP | 10–15% | 14–20% | 18–28% | 多人池再收紧 1–2 档 |
| 冷跟 OOP | 8–12% | 12–18% | 15–22% | 小对子/同花连张为主 |
| 溜入（EP→LP） | 30–40% | 35–45% | 40–50% | 松弱池；不含会加注的强牌 |
| 3-bet | 2–4% | 2–4% | 3–5% | 本桌 `.table_dy` 明确“3-bet 很窄、几乎无诈唬” |
| 3-bet 跟注 | 4–6% | 5–7% | 6–8% | QQ+/AK/AQs 为核心 |

这些数字不是真理，是**起点**；必须用 §8 的回放校准，尤其：
- BB 对 EP 是否真的需要 30%+（前注赔率支持宽，但 OOP 实现率可能打折）；
- 冷跟是否被“跟注站实际会用任何对子/同花 A 跟”拉得更宽；
- 3-bet 是否按桌风收到 2–4%（`.table_dy` 说几乎没有诈唬 3-bet）。

**开注尺寸**：v1 先按位置选表；实际 open ≥9BB 时，把 callers 的范围宽度乘
0.8–0.9 并在渲染里标注（`open 9BB: ranges tightened`），P2 再按尺寸分档。
不要用一个“6BB 表”硬套 15BB 的开注。

#### 数据来源与版权

- 不直接复制第三方 GTO 图表（尺寸/前注/池子都不同，且版权与合规麻烦）。
- 用本仓库自己的 RFI + 公开的赔率/可玩性原则生成；生成脚本和参数一起提交，
  这样表是可复现、可审计的。
- 如要引入外部表，只作为 `source` 标注的对照，不进默认链路。

### 3.4 刷新与防漂移

- `range_data/meta.json` 记录 `open_size_bb / ante / stack / pool / updated / generator_version`。
- 测试 `test_ranges.py::test_generated_data_is_current` 跑 `gen_ranges.py --check`，
  防止“改了 RFI 忘了改 BB 表”。
- `spots.json` 的 `ip_range` 改成从 `RFI` 生成（或直接删字段，让 `board_equity`
  读 `ranges`），消除双份维护。
- 范围 ID 带 `version`，进入缓存 key；改表自动失效。

### 3.5 实时牌面范围（推荐并行做）

除了静态先验，还可以按公共牌实时生成“和牌面有关联”的范围：

- `board_range.build(board, mode, prior)`：对每个 combo 算成牌/听牌/后门/高张，
  得到 0–1.8 的连接度分数；`weight = preflop_weight × score`；
- `mode` 由对手当前街动作决定：`check` 不筛（保留空气）、`call` 低门槛、
  `bet` 高门槛、`raise` 更高；
- 它是**动作条件范围**，不是“他的全部范围”：牌面不会改变他发到什么牌，
  改变的是他继续的范围；
- 分类必须按 **combo + 花色**：`AsKs4d` 上 `7s8s` 是花听，`7h8h` 只是后门顺；
  `QhJh` 是卡顺，不是空气。

原型（`AsKs4d`，阈值 0.3）：纯牌面关联 44.6%；∩ BTN RFI 24.5%；∩ UTG RFI 9.4%。
`AhQh` 对 BTN 关联范围 behind 9.4% / equity 70%，`QhJh` 86.3% / 25%，
`5s6s` 99.5% / 37%。完整设计见
[`docs/实时牌面范围-设计.md`](./实时牌面范围-设计.md)。

## 4. 角色解析：从快照到“每个人是什么范围”

### 4.1 可用的输入

`HandSnapshot` 已经有：

- `opponents: OpponentSnapshot(seat_id, position, stack, folded)`；
- `streets[].actions: ActionRecord(seat_id, position, action, amount, all_in, inferred)`；
- `preflop_shapes`（`unopened / limped / single-raise / three-bet`）；
- `hero_position / hero_is_pfr / pot_type / spr / bomb_pot / blinds / table_size`。

注意 `OpponentSnapshot` **没有**翻前动作，必须用 `ActionRecord.seat_id` 去关联。

### 4.2 算法

```python
# poker_ocr/field_ranges.py
@dataclass(frozen=True)
class FieldRange:
    seat_id: str
    position: str | None
    role: str                  # pfr / cold_call / bb_def / limper / three_bettor / ...
    range_id: str | None       # None = 没把握，降级
    width_scale: float = 1.0   # 画像修正（P2）
    note: str = ""

@dataclass(frozen=True)
class Field:
    ranges: tuple[FieldRange, ...]
    warnings: tuple[str, ...]
```

步骤：

1. 取翻前 `ActionRecord`，按顺序找 `raise/bet`：
   - 0 个加注 + 有人溜入 → **limped**；
   - 1 个加注 → **single-raise**，opener = 那个加注者；
   - ≥2 个加注 → **3-bet+**，opener = 第一个加注者，aggressor = 最后一个加注者。
2. 对每个未弃牌对手（`not o.folded`，排除 hero）：
   - 是翻前最后一个加注者 → `3BET_vs_<bucket>`（3-bet 池）或 `RFI_<pos>`（单加注池的 opener）；
   - 是 BB 且没有加注 → `BB_DEF_vs_<opener>`（单加注池）；limped pot → `BB_CHECK`；
   - 跟注了加注 → BB 用 `BB_DEF_vs_<opener>`，其他人用
     `COLD_CALL_<IP/OOP>_vs_<opener_bucket>`；
   - 溜入 → `LIMP_<bucket>`；
   - 3-bet 池里：第一个加注者（opener）跟了 3-bet → `3BET_CALL_vs_<3bettor_bucket>`；
     其他跟注 3-bet 的人 → 同一张 `3BET_CALL_vs_<3bettor_bucket>`（粗表）。
3. 当前街动作 → 牌面范围 `mode`（只在 postflop 用）：
   - `bet` / `raise` → `bet` / `raise`；
   - `call` → `call`；
   - `check` → `check`（不按牌面筛，保留空气）；
   - 还没行动 → `check`（翻前范围）；
   - 读不到 → `unknown` + warning。
   每个对手可以不同 mode；`hand_vs_ranges` 支持逐对手范围。
4. 与 `preflop_shapes` 交叉校验：
   - 形状说 `single-raise` 但找不到加注者 → 该对手 `range_id=None` + warning；
   - 形状说 `three-bet` 但只找到一个加注 → 同上（OCR 漏读），不要猜。
5. bomb pot → 所有人 `BOMB` 或全部降级；不要套 RFI。
6. 短码（有效筹码 <40BB）→ 仍用表，但加 `warnings`：“short stack, ranges approximate”。

### 4.3 兜底表

| 情况 | 处理 |
|---|---|
| 位置缺失 | `None`，不要用 BB 代理 |
| 动作缺失/`inferred` 且无法判断角色 | `None` + `Data gaps` |
| 只观察到最后一条街 | 只用能确认的角色；其余 `None` |
| 空范围 / 全员弃牌 | `None` |
| 4 个以上对手 | 只算前 4 个（或全部算但渲染截断），标注 |
| 3-bet/4-bet 无表 | `None`，明确说“range unavailable”，不要拿 SRP 表套 |

## 5. 计算引擎

### 5.1 API

```python
# poker_ocr/hand_vs_ranges.py
@dataclass(frozen=True)
class OpponentEdge:
    seat_id: str
    position: str | None
    range_id: str
    width_pct: float               # 范围原始宽度（去重牌前）
    combos_after_removal: int
    behind: float                  # 0..1，严格大于我
    tie: float
    ahead: float                   # 1 - behind - tie
    beaten_by: tuple[RangeGroup, ...]   # 按牌型/牌力分组，范围加权
    examples: tuple[str, ...]           # 例如 ("77 x3", "K7s x2")

@dataclass(frozen=True)
class HandVsRanges:
    hero: str
    board: str
    street: str
    opponents: tuple[OpponentEdge, ...]
    behind_any: float
    tie_any: float
    equity: float
    equity_ci: float
    samples: int
    warnings: tuple[str, ...]

    def render(self) -> str: ...
```

### 5.2 计算步骤

1. **校验**：board 3–5 张、hero 2 张、无重复牌；范围 1–4 个；否则 `None`。
2. **去重牌过滤**：每个范围去掉含 hero/board 牌的组合；剩余权重为 0 的组合不参与。
   过滤后为空 → 该对手 `None`；全部为空 → `None`。
3. **逐对手精确统计**（不用采样）：
   - 对每个剩余组合 `h`，算 `evaluate(list(h)+board)` 与 hero 比较；
   - 按权重累加 `behind / tie / ahead`；
   - 按 `(category, 主牌力)` 分组，记录权重、组合数、2 个示例；
   - 这一步是 **5ms 量级**，不要省。
4. **联合 `behind_any` / `tie_any`**：
   - 每次试验独立抽每家一手牌；**整组**检查是否互相撞牌，撞了就整组重抽；
   - 如果某家当前成手牌严格大于 hero，记 `behind_any += 1`；
   - 如果没人严格大于、但至少一家与 hero 相等，记 `tie_any += 1`；
   - 为什么整组重抽：先抽 A 再按“排除 A 的牌”抽 B，会引入与 `1/Z(A)` 有关的
     归一化因子，联合分布不是“范围乘积在不去重条件下的均匀分布”，有系统偏差。
     整组拒绝重抽才是正确的条件分布。
5. **`equity`**：
   - 同一组手牌，发完剩余公共牌（flop 发 2、turn 发 1、river 发 0）；
   - 与 hero 比大小；赢记 1，平局按 `1/赢家数` 分池；
   - 2000 次的标准误约 ±1.1%（p=0.5），报告 `±`。
6. **`draw_share`（P1，可选）**：
   - 对每个范围组合算强听（8+ outs）占比；flop/turn 才有意义；
   - 用来解释“为什么 `behind_any` 高/低但 equity 不低”；
   - 实现可复用 `coach._count_outs`，先抽样 200 个组合控制耗时。
7. **缓存**：
   - key = `(street, board, hero, tuple((id, version) ... ), samples, seed_version)`；
   - `lru_cache(maxsize=256)`；范围/版本变了自动失效；
   - 同一决策点重复调用 <1ms。

### 5.3 几个容易错的点

- **平局不是领先**：`ahead = 1 - behind - tie`；渲染时把 tie 单独写。
- **river 不发牌**：`remaining = 5 - len(board)`，不能固定发 2 张。
- **权重 0 的组合**：既不能参与 behind 统计，也不能被采样到。
- **同一范围出现两次**（两个冷跟都用同一张表）：允许；采样时按两家独立抽，
  但要在 `warnings` 标“caller ranges are independent draws”。
- **范围相关性**：两个 caller 的范围都受 opener 影响，现实中有相关性；独立抽样
  是近似。不要在这个版本上做联合范围模型，先把单范围做对。
- **`behind_any` 的独立性近似**：`1-∏(1-behind_i)` 只能当 sanity check；
  它忽略了对手之间的去重牌相关，和 MC 可能差 1–2 个百分点。默认用 MC。
- **确定性**：用 `(street, board, hero, range_ids)` 的稳定 hash 派生 seed
  （不要用 Python 内置 `hash()`，进程间会变）；同一决策点反复渲染数字不变。

### 5.4 性能

原型（Python 3.12，本机，`.venv`）：

| 场景 | 样本 | 耗时 |
|---|---|---|
| 逐对手精确 behind（3 个范围） | — | ~5ms |
| 3-way MC（含 behind_any + 发牌） | 2,000 | ~80ms |
| 4-way MC | 1,500 | ~80ms |

优化顺序（如果不够快）：

1. 默认 3-way 2,000 / 4-way 1,500；`HAND_VS_RANGES_SAMPLES` 可调；
2. 预计算每个范围的 combo 列表和 `evaluate` 局部变量绑定；
3. 缓存 `(range_id, dead_cards)` 过滤后的组合；
4. 回放/批量场景（replay-console）默认关掉或降到 500 次；
5. 不要用 Python 并行——GIL 下线程没收益，多进程又会复制范围数据。

### 5.5 失败语义

返回 `None` 的条件（一条即够）：

- 没有范围 / 范围为空 / 过滤后无组合；
- board 不足 3 张、hero 不足 2 张、重复牌；
- 对手位置/角色无法确认；
- 3-bet/4-bet/limped 没有对应表且不允许降级。

`None` 时提示词保留“random-hand lower bound”，并加一行 `Data gaps`，
不要伪装成范围基准。

## 6. 渲染与提示词

### 6.1 事实块（示例，数字来自原型，仅演示格式）

TPTK，3-way（BTN 开池、CO 冷跟、BB 防守；CO 用临时手写范围，BB 仍用当前静态 44%）：

```text
## Hand vs ranges (3-way: BTN open, CO cold-call, BB defend)
Board: Ks7d2c | Your AhKd | flop | 2000 samples
Ranges: BTN RFI 44.8% | CO cold-call 16.4% | BB defend 43.9% (current static, illustrative)
Equity vs field (by river): 60% ±1%
Made hand now: behind at least one 14% | per opponent: BTN 3.6% (tie 1.3%), CO 6.2% (3.7%), BB 2.9% (1.3%)
Behind (BTN range): sets 1.6% (KK x1, 77 x3, 22 x3), two pair 1.3% (K7o x4, K7s x2), AA 0.7%
Read: TPTK is ahead of all three ranges now; the 60% vs 14% gap is draws and multiway runouts, not current strength.
```

坚果花听，同一牌面结构（`AhQh` on `Kh7h2c`）：

```text
## Hand vs ranges (3-way: BTN open, CO cold-call, BB defend)
Board: Kh7h2c | Your AhQh | flop | 2000 samples
Ranges: BTN RFI 44.8% | CO cold-call 16.4% | BB defend 43.9% (current static, illustrative)
Equity vs field (by river): 44% ±1%
Made hand now: behind at least one 87% | per opponent: BTN 40.0% (tie 2.0%), CO 60.5% (5.6%), BB 43.0% (2.0%)
Behind (BTN range): one pair 36%, sets 2%, two pair 2%; ahead now: air 58%
Read: behind now, but 44% equity — this is a draw, not a made hand; judge it by outs and price, not by the made-hand rank.
```

要点：

- 标题写清人数和角色（谁开、谁跟、谁是 BB）；
- 每个范围给**原始宽度**和样本数，让模型知道这是先验不是精确值；
- `Equity` 与 `behind now` 必须分开写，且各自带“by river / now”标签；
- `Behind` 分组用“牌型 + 具体牌”而不是只给一个百分比；
- 4 个对手时每对手一行会太长，按“最危险的两家 + 其余合并”截断；
- 末尾一句 `Read` 只做“这两个数怎么读”，不要替模型做下注决定。

### 6.2 提示词改动

1. `Situation` 增加 `hand_ranges: "object | None"`；`build_situation` 里
   在 `board_equity.lookup` 之后 try/except 调用 `hand_vs_ranges.lookup(sit)`。
2. 事实块位置：放在 `ground_truth` 之后、`board_eq` 之前（它是主答案，
   board structure 是背景）。
3. `_LEAN_SYSTEM` 的 `## Priority` 改成：

   ```text
   1. Hard math / computed facts (pot, price, equity, behind-now, SPR)
   2. «Hand vs ranges» — use it for “what he has”, not the random-hand rank
   3. «Board structure» / «GTO baseline» — background only
   4. Generic heuristics
   5. Opponent/table profile — an explicit OVERRIDE on the range baseline, not a replacement for math
   ```

4. 新增口径规则（简短，别写成小作文）：

   - “Equity vs field” is the number to compare with break-even; “behind at least one”
     is about the **current made hand**, not equity.
   - A draw can be behind now and still have equity; never fold a draw because
     “behind now” is high.
   - When a range block exists, the random-hand rank is a LOWER bound on how strong
     their range is (so an UPPER bound on your equity), not a description of the
     range; do not quote it as “his range”.
   - If a seat has no range, say “range unknown” and fall back to the random lower
     bound; never invent a range.
   - A station/LAG profile widens/narrows the baseline; it never overrides the
     computed equity.

5. 把手写的冷跟/BB/3-bet 段（`_LEAN_SYSTEM` 2026–2029）改成由 `ranges.py`
   生成的文本（类似 `chart_text()` 的思路），避免“代码用一套、提示词写另一套”。
   `THREE_BET_VALUE/BLUFF` 要么删除，要么变成生成器的输入。
6. 旧的 random 行改标题：

   ```text
   Made-hand rank vs RANDOM hands (lower bound): ...
   ```

   不要删掉它——它是范围缺失时的唯一基准，也是 sanity check。

7. 控制长度：新块目标 8–12 行 / ~700 字符；`_LEAN_SYSTEM` 的新增规则控制在
   ~400 字符。现有 `test_lean_prompt_is_compact_and_range_based` 的系统提示上限
   是 12,600，新增后要重新量。

### 6.3 模型行为验收

- 模型引用“sets / two pair / AA”“one pair / air”等类别，而不是只引用一个随机牌百分比；
- 面对花听时，不会因为 `behind now` 高就弃牌，而是引用 `equity` 和赔率；
- 面对 TPTK 时，不会把 60% equity 说成“现在大幅落后”；
- 范围缺失时明确说“range unknown”，不编造。

### 8.2 暴力枚举对照（关键）

选两个小范围（例如各 15–25 个组合）、river 牌面（不测发牌）：

- 枚举所有**不撞牌**的组合对，算 `behind_any`、`equity`；
- 与 MC 对比，允许 ±2%（2000 次）；
- 再测一个 flop 场景，用第二个独立 MC（不同 seed）对比，不要求精确。

### 8.3 20–30 手回放校准

- 数据来源：`hands/1023.hands.json`（109 手）、`hands_review.csv`、`logs/`、
  `replay-console`；
- 覆盖 3/4/5 人池、flop/turn/river；
- 对比：
  - random `beat_pct` vs range `behind_i`：**方向不固定**——紧范围去掉了垃圾两对，
    也可能让“范围内比我大的比例”下降；重点看差异是否符合范围构成，
    不要假设“范围一定更高”；
  - MC equity vs 小范围枚举；
  - “领先/落后”类别是否符合直觉；
  - 同一手在新旧提示词下的选项差异（记录，不自动判好坏）。
- 结论写回文档：哪些范围明显偏宽/偏紧，阈值怎么调。

| P0 | `ranges.py` + 数据文件 + RFI 生成 + `field_ranges` 骨架（先用现有 `spots.json` 范围跑通） | 0.5–1 | 能按快照给每个对手一个范围 ID；缺数据返回 None |
| P1 | `hand_vs_ranges.py` + 精确统计 + MC + 缓存 + 单测 | 1–1.5 | 3-way 端到端出数；暴力枚举对照通过 |
| P2 | `gen_ranges.py` + BB/冷跟/溜入/3-bet 表 + 人工复核 | 1.5–2.5 | 表宽度/底部手牌合理；`--check` 通过 |
| B（并行） | `board_range.py` + 动作 mode + 分类测试 | 2–3 | `AsKs4d` 的 `25/34/5s6s/7s8s` 正确；`7h8h` 排除；<50ms |
| P3 | 渲染 + 提示词优先级 + 手写段替换 + golden 更新 | 0.5–1 | 模型引用类别；random 行降级 |
| P4 | 20–30 手回放校准 + `board_equity` 重构（可选） | 1 | 无明显荒唐结论；回归全绿 |

**合计 4.5–7 个工程日**（不含持续的数据调优）。
**最小可用切片**：P0 + P1 + 一个 BTN/CO 开池 + BB + 一个冷跟，约 **2 天**，
已经能回答“我这手牌在他们范围里大概什么位置”。

关键路径是 **P2 的数据**，不是 P1 的代码。如果只有 2 天，先做“BTN/CO 开池 +
BB + 一个冷跟”，不要摊大而全的表。

## 10. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 范围口径错（GTO vs 池子） | 算得越准越误导 | 明确默认“描述性池子先验”；画像修正；文档写清口径 |
| 6BB/9BB 开注尺寸不匹配 | 跟注范围整体偏移 | 按实际 `ActionRecord.amount` 分档/缩放；meta 记录 |
| 位置/动作 OCR 错 | 角色错、范围错 | 与 `preflop_shapes` 交叉校验；不确定就 None |
| 对手间范围相关 | `behind_any`/equity 偏差 | v1 独立抽样 + warning；不在 v1 做联合模型 |
| MC 噪声 | 同一手数字跳动 | 固定 seed、2000 次、报告 ±；同 key 缓存 |
| 提示词冲突 | 模型混用 random/range | 改标题、优先级、规则；回放验证 |
| 性能 | 回放批处理慢 | 缓存、样本可调、批量默认关 |
| 模型过度信任 | 范围错时更自信 | 显示范围宽度/来源；缺数据明确降级 |
| 数据漂移 | RFI 改了表没改 | 生成 + `--check`；单一数据源 |
| 版权/合规 | 外部图表 | 自生成；外部表只做对照 |
| 纯牌面范围当成“全部范围” | 删掉空气，高估对手 | 按动作选 mode；过牌用翻前范围；见 §3.5 |
| 范围越做越大 | 工期失控 | 位置桶、v1 只做 SRP + limped；3-bet 先粗表；不碰 184/多人 GTO |

**不要做**（重申文档结论）：

- 不要为这个目标继续跑 184 类 solver；它 HU、消费范围、不回答 hand vs range。
- 不要做 3–5 人 GTO 均衡；成本极高，范围噪声大。
- 不要把 `beat_pct`（随机牌）当“对他们的范围领先多少”。
- 不要在 v1 做翻前 solver；标准表 + 校准足够。

## 11. 需要拍板的三件事

1. **默认口径**：贴现场松弱池（描述性，推荐）还是贴 6BB GTO（规范性）？
   推荐前者；后者作为“未知紧手”的回退先验保留。
2. **limped / bomb pot 是否进 v1**：推荐 limped 进（现场太常见），bomb 先降级。
3. **画像宽度修正是现在做还是 P2**：推荐先做基础范围 + 文本画像，等
   `hand_vs_ranges` 跑通后再接 `vpip/pfr` 数值缩放；否则两个变量一起调，无法归因。

如果这三个口径不先定，P2 的数据会反复返工。

## 附录 B：原型实测记录

环境：`.venv`，Python 3.12.13，本机；范围用 `spots.json` 的 BTN RFI（570 组合，
43.0%）、一个临时手写 CO 冷跟（218 组合，16.4%）、当前静态 BB 防守（582 组合，
43.9%）。

| 场景 | 结果 |
|---|---|
| `AhKd` on `Ks7d2c`，3-way | behind_any 13.7%，equity 59.7%；逐对手 behind 3.6% / 6.2% / 2.9% |
| `AhQh` on `Kh7h2c`，3-way | behind_any 87.0%，equity 44.2%；逐对手 behind 40.0% / 60.5% / 43.0% |
| 3-way 2000 次（含 behind_any + 发牌） | 83.6ms |
| 4-way 1500 次 | 81.3ms |
| 逐对手精确 behind（约 1,400 组合） | 5.0ms |
| `evaluate` 单次 | 4.55µs |

注意：

- 这些数字是**原型口径**，不是最终范围；冷跟范围是临时手写的，BB 仍是静态 44%。
  它们只用于证明“引擎可行、量级正确”，不能当验收数据。
- `behind_any` 与 `1-∏(1-behind_i)` 可能差 1–2 个百分点（去重牌相关 + 采样噪声），
  以 MC 为准，乘积只做 sanity check。
- 4-way 2000 次会接近/超过 100ms；默认 1500 次，或按机器自适应。
