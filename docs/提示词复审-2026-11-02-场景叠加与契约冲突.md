> 结论先行：**2026-11-02 那轮修掉的是「单条规则写错」，这一轮暴露的是

## 一、复审范围与判定口径

本次只看 live 链路：

- system：`prompt/system/{intro,output,priority,decision,metrics,stack,ante,scenario}.py`
- user：`prompt/user/{situation,geometry,position,price,explosive,action_line,preflop,strength,ranges,profiles,table_stats,notes,attack,quality,options}.py`
- 组装：`prompt/system/__init__.py`、`prompt/user/__init__.py`
- 契约/版本：`prompt/version.py`、`prompt/shared/{format,labels}.py`
- `prompt/offline/` 是旧英文审计层，不进入 live prompt；本轮不把它算作 live
  冲突，只在需要说明「旧规则没有回流」时提及。

判定为**规则冲突**的三种情况：

1. **同一局面、两句话可以导出相反动作**（例如「无位置默认过牌」与
   「无位置用下注/过牌-加注定义底池」同时出现）。
2. **同一个词在两处表示不同数值/不同对象**（例如「后手」在一处是剩余筹码，
   另一处是「剩余+本街已下注」）。
3. **契约引用了事实块没有提供的东西，或事实块给了契约不允许的动作**
   （例如河牌说「按对手范围判断」但没有范围段；输出契约说 `call` 只用于
   补盲/过牌，但翻前事实说「可以跟注」）。

不把「默认」当成绝对规则，但要求：**默认句必须和例外句在同一段里，
或者由更高优先级的段落明确覆盖**；否则模型只能按阅读顺序猜。

## 二、P0：会直接改变动作的冲突

### P0-1 五个场景段可叠加，但没有优先级

**代码**：`system/scenario.py:97-104` 把五个函数注册进 `SCENARIO_SECTIONS`；
`system/__init__.py:44` 无差别 `extend` 所有命中的段。五个条件分别看
「Hero 总筹码」「在局对手数」「是否听牌」「是否河牌」，**不是互斥条件**。

**实例 A：18BB、单挑、无位置、同花听牌**

同一份 system 同时出现：

| 段 | 原文 | 对同一动作的指向 |
|---|---|---|
| 短码 `scenario.py:25-27` | 「后手 ≤20BB 时，优先把 all-in 或弃牌当作默认分支」；「听牌只按即时赔率算，不要假设中牌后还能收钱」 | 全下/弃牌；不要用隐含赔率 |
| 单挑 `scenario.py:37` | 「无位置时用下注或过牌-加注主动定义底池」 | 主动下注/加注 |
| 听牌 `scenario.py:41-42` | 「强听……才考虑半诈唬，多人池或无位置默认过牌」；「用赔率 + 隐含赔率 + 对手线路」 | 默认过牌；要用隐含赔率 |

这不是「通用规则 vs 场景规则」，而是**三个场景规则彼此冲突**。模型没有
任何文本告诉它「短码优先于单挑」还是「听牌优先于短码」。按阅读顺序，
听牌段在最后，模型很可能按「无位置默认过牌」打；按短码段，又可能直接推。

**实例 B：4 人池、河牌、无位置、两对**

- 多人池 `scenario.py:33`：「无位置默认过牌控池」
- 河牌 `scenario.py:47`：「价值下注只问『更差的牌会不会跟』」
- 恒定段 `decision.py:14`：「非坚果默认不打三条街」

三句话都能用到这一手：两对不是坚果，按多人池应控池，按河牌价值下注又该
在更差的牌会跟时下注。模型可以合理化 check，也可以合理化 bet。

**实例 C：短码 + 河牌面对加注**

- 短码 `scenario.py:25`：「优先把 all-in 或弃牌当作默认分支」
- 河牌 `scenario.py:48`：「被加注时按赔率 + 对手范围判断，不默认弃」

一个说优先弃，一个说不默认弃。

**根因**：`docs/提示词模块拆分-2026-11-03.md:150-153` 的约束只写了
「一段一场景」，没有写「多个场景同时成立时谁优先」；`build_system` 也没有
仲裁层。上一轮审阅反复强调的「没有仲裁」在场景层又出现了一次，只是从
「恒定段里规则打架」变成了「条件段之间打架」。

**建议**（需要产品先拍板，不能靠调顺序解决）：

1. 给场景段加一张**冲突矩阵**（见 §五.1），明确「短码只约束翻前」「翻后
   按 SPR/人数」「听牌只约束下注/半诈唬」「河牌只约束摊牌/价值」。
2. 更彻底：把短码段改成 `if street == PREFLOP` 才出现；翻后短码由 `stack.py`
   的 SPR 规则覆盖。这样短码+单挑+听牌只剩「单挑 vs 听牌」一对冲突。
3. 每个场景段末尾加一句「本段不覆盖 X 段；冲突时按 §五.1」。
4. 加测试：至少覆盖 `短码+单挑+听牌`、`短码+听牌`、`多人池+河牌`、
   `短码+河牌` 四组，断言不出现互相否定的短语对（见 §五.6）。

### P0-2 「后手」同词不同义，同一份 prompt 出现两个数字

**代码**：

- `user/situation.py:34-37`：`Hero：…｜后手 {snap.hero_stack}BB`，这里是
  **剩余筹码**。
- `system/scenario.py:21`：短码线用 `_hero_total_stack(snap)`，注释写
  「Hero 后手（含本街已下注）」；`scenario.py:57` 把它渲染成
  「## 场景：短码（Hero 后手约 {stack}BB）」。
- `poker_ocr/options.py:126-129`：全下 note 用 `hero_max = hero_bet + stack`，写
  「实际后手 {hero_max}BB；有效筹码只有 {effective}BB」。
- `system/decision.py:15`：「后手 ≤20BB 的翻前推/弃区全下是标准动作」，
  这里「后手」没有定义是哪一个。

**渲染证据**（`hero_stack=18`、`hero_bet=1`）：

```
## 场景：短码（Hero 后手约 19BB）
Hero：BTN｜底牌 Ah Kd｜后手 18BB
- all-in｜全下 18BB（实际后手 19BB；有效筹码只有 18BB，多出的 1BB 不会被跟）
```

同一份 prompt 里「后手」是 18 还是 19？模型无法知道。更常见的情况是
`hero_stack=18`、`hero_bet=4`：本手总筹码 22 > 20，短码段不出现，但
`decision.py` 按「后手 18BB」仍会说「≤20BB 推/弃区」。**同一个阈值，
一个按剩余筹码、一个按总筹码，会系统性漏掉或误加短码规则。**

**建议**：

- 在 `shared/labels.py` 或 system 的筹码段固定词表：
  - `后手` = 剩余筹码（`hero_stack`）；
  - `本手总筹码` = 后手 + 本街已下注（`_hero_total_stack`）；
  - `有效筹码` = min(本手总筹码, 对手本手总筹码)；
  - `可玩深度` = min(我的后手, 最深未弃牌对手的后手)。
- 短码段标题改成「本手总筹码约 19BB」或直接按「后手」触发；二选一，
  但触发和文案必须同口径。
- `decision.py` 的「后手 ≤20BB」改成「后手 ≤20BB（本手总筹码见「筹码深度」）」，
  或统一按总筹码。
- `all-in` 标签改成「全下 19BB（有效 18BB，多出 1BB 退回）」，不要在同一行
  同时出现两个都叫「后手」的数字。

### P0-3 翻前范围结论仍是「两个动作」，并且绝对禁止平跟

**代码**：`situation.py:194-204` 的 `_range_conclusion_zh`。

渲染 QTo（BTN，3 个溜入者）：

```
翻前范围结论：QTo 在 BTN 的开池范围内；前面有 3 个溜入者，
收紧范围（≈LJ）已不包括它 → 默认弃牌，不要平跟
```

渲染 44（同局面）：

```
翻前范围结论：44 在 BTN 的开池范围内；前面有 3 个溜入者，
收紧范围（≈LJ）仍包括它 → 可以加注隔离，不要平跟
```

三个问题：

1. 第一句「在开池范围内」和第二句「默认弃牌」在同一行，模型仍可以抓住
   前半句作为开池理由。上一轮 P0-7 要的是「单一动作」，现在只是把两个
   结论都写得更长。
2. 「不要平跟」是绝对句，但 `decision.py:7` 说「非盲位平跟是例外」，
   `output.py:13` 说 `call` 允许「明确的 limp 例外」。三处口径不一致。
3. `hand_track.py:1462-1478` 的注释明确写「溜入池里平跟（over-limp）是
   正常线路，尤其是小对子抽 set」；当前范围结论对小对子也说「不要平跟」，
   与代码自己的口径相反。

**建议**：

- 改成「一个主动作 + 一个条件例外」，例如：
  - `QTo：3 个溜入者后收紧范围（≈LJ）外 → 默认弃牌；要玩就加注隔离，
    不要平跟。`
  - `44：可以加注隔离；若桌松、后手深，也可按约 10:1 隐含赔率平跟抽 set
    （非盲位平跟的例外）。`
- 或者明确产品口径「本产品不 over-limp」，然后删除 `decision.py` 的
  「例外」和 `preflop` 注释，三处一起改。不能一处禁止、一处允许。
- 当前测试 `tests/test_advice.py:4703`、`:4718` 把「默认弃牌，不要平跟」和
  「可以开池加注，不要平跟」锁死了；改口径时必须同步改测试，否则测试会
  保护旧冲突。

### P0-4 行动线的「（无行动）」在动作缺失时与底池/动作矛盾

**代码**：`user/action_line.py:31-32`：

```python
if not actions:
    return "（无行动）"
```

**渲染证据**：

- `flop_default`：翻前显示「（无行动）」，但同一份 prompt 写
  「底池类型：单加注池」「底池 6BB」「本手已投入 3BB」。
- `river_face_jam`：河牌显示「（无行动）」，但「需跟 50BB」、
  `## 数据质量` 写「有下注额但没抓到动作徽章，范围按更宽处理」。
- 0 对手异常帧：翻牌显示「（无行动）」，但底池 20BB，翻前底池 6BB。

`output.py:17` 要求「没人行动过不能写『对手过牌』」；但行动线自己先说
「无行动」，模型写「对手过牌」时反而与行动线一致。这是**事实层内部
自相矛盾**，也是模型给 reason 编动作的入口。

**建议**：

- 把「无行动」改成「未记录到行动」或「动作未捕获」。
- 有底池变化时补一句「本街底池 X→Y」，让模型知道「没记录」不等于
  「没人下注」。
- 数据质量段按街/按座位写「本街动作未捕获」，不要只在 section 级写一句。
- 测试：`test_prompt_contains_full_action_line_and_options` 之外，加
  「底池变化 > 0 且 actions 为空 → 不得出现『（无行动）』」。

### P0-6 事实优先级与「最后读到裁决」互相矛盾

**代码**：`system/priority.py:6-12`：

```
1. 硬事实 … 2. 确定性计算 … 3. 模型估计 … 4. 现场观察 … 5. 通用经验。
4. 现场观察：… 与 3 冲突时写出两者、不默认谁优先，但不得压 1/2。
同一层内"更具体"优先… 文字建议块（攻击/桌况读法）不是硬事实，
不能压画像/观察；最终按本表仲裁。
```

三处内部矛盾：

1. 标题说「序号小者优先」，第 4 条又说「与 3 冲突时不默认谁优先」——
   序号 3 < 4，按标题应 3 优先，按条文又没有优先级。
2. 第 4 条说「写出两者」，但 `output.py:8` 只允许一个 `reason` ≤40 字，
   没有「两者」的字段。
3. 「文字建议块……不能压画像/观察」，但 `user/__init__.py:85` 的注释说
   攻击/剥削块「放在统计与观察之后，模型最后读到裁决」；实际 prompt 里
   `## 攻击机会` 的「结论」确实在画像、桌况、人工观察之后。**优先级说它
   不能压，排版却让它最后发声。**

另外，priority 只点名「攻击/桌况读法」两个建议块，但事实块里至少还有：

- `situation.py:194-204` 的范围结论（默认弃牌/可以开池）；
- `preflop.py:250-295` 的「可以跟注/默认弃牌/可以 4-bet」；
- `strength.py:116-123` 的 combo draw「可作为保护/半诈唬下注」；
- `ranges.py:258-285` 的「范围警告……不要拿『我现在有牌』当跟注理由」；
- `explosive.py:32-35` 的「按正常翻后规则打」。

它们都没有层号，模型只能当事实读。

**建议**：

- 先拍板 3 和 4 谁优先。建议改成「3 优先；4 是 3 的输入之一，冲突时在
  reason 里写『观察与统计相反』，但动作按 3」；或者反过来「4 优先」。
  不要保留「不默认谁优先」。
- 给「程序建议」单独一层（例如 3.5），并明确「建议不覆盖 1–4，只覆盖 5」；
  或者把建议移到独立的 `## 程序建议（不是事实）` 段，priority 里点名。
- 攻击块要么放在画像之前（作为「候选方向」），要么在块内加
  「以下是程序建议，不是事实；与逐座位画像冲突时以画像为准」。
- 删掉 `user/__init__.py:85` 的「最后读到裁决」表述，或改掉 priority。
- 「写出两者」改成可执行的形式：`reason` 里只写「观察与统计相反，按统计」，
  或新增 `conflict` 字段（但这会改输出契约）。

### P0-7 「硬缺口」清单与数据质量段不一致

**代码**：

- `system/output.py:18` 定义硬缺口为：**底牌/公共牌/底池/需跟/后手/在局人数**；
  「范围/画像/桌况缺口不改变价值下注/弃牌，只降低诈唬频率」。
- `user/quality.py:53-56` 把「翻前动作线缺失」也算进 `hard`：
  ```python
  hard = [g for g in rest
          if ("未读全" in g or "筹码未读出" in g or "状态帧" in g
              or "翻前动作线缺失" in g)]
  ```
- `quality.py:26` 对 `no preflop action` 的输出是「翻前动作线缺失，翻前形态/PFR
  未知（**按未知处理**）」；`system/decision.py:7` 却说「形态未知/动作线缺失时
  不主动平跟，**按未开池处理（open 或弃）**」。
- `quality.py:34` 把 `board incomplete` 翻成「牌面缺张，该街动作未计入范围」，
  但它不在 `hard` 列表里；按 `output.py:18`，公共牌缺失应是硬缺口，可能被
  4 条上限挤掉。

**后果**：模型看到「翻前动作线缺失」被列在数据质量段（而且 `_summarize_gaps`
把它排在最前），会按硬缺口走保守线；但 system 说按未开池 open/fold。两个
默认方向相反。反过来，「牌面缺张」可能被当成普通范围缺口，模型继续做价值
下注/弃牌，而 output 契约认为它该走保守线。

**建议**：

- 数据质量段直接输出两类标签：
  ```
  - 硬缺口：底池未读全、后手未知 → 走保守线
  - 范围缺口：3 名对手范围未知 → 只降低诈唬频率
  ```
  不要让模型自己从中文句子里猜类别。
- 把 `output.py:18` 的清单和 `quality.py` 的 `hard` 列表合成一个常量
  （例如 `HARD_GAP_KINDS`），两边引用同一份。
- 「翻前动作线缺失」二选一：要么算硬缺口并删掉 `decision.py` 的「按未开池
  处理」，要么不算硬缺口并把 `quality.py` 的 `hard` 列表改掉。
- 「牌面缺张」明确归入硬缺口（公共牌）。

### P0-9 河牌要求「按对手范围判断」，但范围段可能整个不存在

**代码**：

- `scenario.py:48`：同样要求「按赔率 + 对手范围判断」。
- `strength.py:136-145`：`hand_ranges is None` 时只给

- `ranges.py:187-189`：`hr is None` 直接 `return []`，不会出现

**渲染证据（河牌，面对 50BB 全下）**：

```
## 实时牌力
…
当前成牌落后至少一家：9.5%（按随机牌下界；这是当前五张被至少一家压过的概率，
```

## 三、P1：会系统性带偏、但通常不直接翻盘

### P1-1 「多人池」在 3 人还是 4 人，代码/README 三套口径

- `decision.py:10`：「多人池（含 Hero）：4 人以上顶对/超对降级，3 人池 SPR<3 可套池」；
- `stack.py:9`：「单挑/3 人池顶对可套池，4 人以上降级」；
- `scenario.py:61-65`：`opponents >= 2` 就出「## 场景：多人池（本手 3 人）」；
- `README.md:117`：「多人池（3 人以上）」；
- `README.md:127`：「人数口径分『单挑 / 3 人池 / 多人池（4+）』」。

同一份 README 里 3+ 和 4+ 各写一次；prompt 在 3 人时标题写「多人池」，
但降级规则只在 4+ 生效。模型会不知道 3 人池算不算「多人池」。
**建议**：只保留一个定义；如果保留「3 人池」独立档，场景段标题改成
「3 人池」并用不同函数，不要复用「多人池」这个名字。

### P1-2 20BB 与 SPR 3.0 的边界同时命中两套规则

- `stack.py:9`：「SPR 低（<3）……顶对可套池」；
- `scenario.py:26`：「翻后 SPR ≤3 时顶对可以套池」；
- `decision.py:10`：「3 人池 SPR<3 可套池」；
- `stack.py:10`：「20–40BB 仍是正常加注」；
- `scenario.py:25`：「后手 ≤20BB 时，优先把 all-in 或弃牌当作默认分支」；
- `decision.py:15`：「后手 ≤20BB 的翻前推/弃区全下是标准动作」。

20BB 正好同时属于「20–40 正常加注」和「≤20 推/弃」；SPR 3.0 正好同时属于
「<3 低 SPR」和「≤3 可套池」。这类 boundary 冲突不需要模型推理，只要数字
刚好落在边界就会随机选一边。
**建议**：所有阈值统一成半开区间（例如 `[20, 40]` 与 `<20`，或 `≤20` 与
`>20`），并在 `shared/labels.py` 或 `pot_math.py` 放常量，模板引用常量，
不要手写。

### P1-3 范围段的「本街还没有动作」是全局句，但经常只有部分座位没动作

`ranges.py:213-216`：

```
- 本街还没有动作：范围沿用翻前先验，不是已过牌
```

触发条件是 `edge.mode == "unacted" and not edge.events`。在多人池转牌，
BTN 已经下注、Hero 已经过牌，这句话仍然出现（`multiway_turn_draw` 渲染
实测）；在多人池河牌，CO 已经过牌，这句话也仍然出现。它想说的是
「UTG/LJ 还没动作」，但读者会理解成「本街没有任何动作」，与行动线直接
矛盾。
**建议**：改成「以下座位本街未动作：UTG、LJ（范围沿用上一街，不是已过牌）」，
按座位列出；不要用无主语的全局句。

### P1-4 数据质量的「本街行动线缺失」同样是全局句

`quality.py` 把 `no action this street` 翻成「本街行动线缺失，范围按未行动
处理（不是已过牌）」。在 BTN 已经下注的转牌，这句话仍会出现；它实际只
描述 UTG/LJ。与 P1-3 同源。
**建议**：数据质量按座位/按街归因；如果是「部分座位未动作」，写清楚是哪
几个座位，不要写「本街缺失」。

### P1-5 「身后的 UTG」把位置词当行动顺序词

`preflop.py:244-249`：

```
面对加注：3-bet，LJ 再加注到 10BB；身后的 UTG、BB 还没响应加注
```

Hero 是 CO，UTG 在 Hero 前面（位置更早），只是本轮还会再说话。用「身后」
会与 system 的「位置=翻后座位顺序」和 `position.py` 的「身后」混在一起。
**建议**：改成「本轮还要响应加注：UTG、BB」；把「身后」严格限定为座位
顺序在 Hero 之后。

### P1-6 c-bet 只有一个「桌级」抑制，逐座位「可剥削」仍可给出相反建议

`user/__init__.py:67-74` 用 `attack` / `trap_reads` 抑制桌级 c-bet 建议；
`table_stats.py:169-175` 只把 `suppress_cbet` 传给 `table_exploit_zh`。
但 `opponent_profile.render_reads_zh` 仍会逐座位输出：

- `opponent_profile.py:2664`「过牌-加注频繁 —— 别对他的过牌随手开火」
- `opponent_profile.py:2670`「跟 c-bet 多 —— 别用空气开火」
- `opponent_profile.py:2706`「对 c-bet 弃得多 —— 干燥面可以开火」

在「桌况整体跟 c-bet 多」但「某个座位对 c-bet 弃得多」的桌上，攻击块可能
说「跟着过牌」，逐座位画像却说「可以开火」；priority 又说逐座位 > 本桌。
「单一裁决」实际上没有单一 owner。
**建议**：做一个 `resolve_cbet(sit)`，同时消费逐座位 xr/call/fold、桌级
c-bet、攻击块，输出**一条**「开火/不开火/仅强牌」；画像段只保留描述性
数据（「对 c-bet 弃 68%」），不再输出动作建议。

### P1-7 事实块里的建议没有标注，priority 只点名了两个块

除 P0-6 已经点名的攻击/桌况读法，以下都是建议，但排在事实块里：

### P1-8 输出契约的 `call` 映射在「面对加注」时含糊

`output.py:13`：

```
翻前无人入池用 open-*/call；call 只用于 SB 补盲、BB 过牌和明确的 limp 例外。
翻前面对加注用 raise-3x/raise-4x…
```

第二句没有说「面对加注也可以 call」，而第一句的「call 只用于」是绝对句。
渲染的 3-bet 局面却同时有：

```
对加注的牌力：AKo … → 可以跟注，不 4-bet
- call｜跟注 10BB
```

模型如果严格读契约，会认为 `call` 不合法，只能 4-bet 或弃牌。
**建议**：把第一句限定为「无人入池时」；另加一句「面对加注时 call=跟注，
raise-3x/4x=再加注」。同时检查 `open-*` 在短码全下局面不存在时，契约不要
要求 `open-*`。

### P1-9 `reason ≤40 字` 与「说明缺什么」互相打架

- `output.py:8`：`reason` ≤40 字；
- `output.py:18`：硬缺口时「并在 reason 说明缺什么」；
- `advice.py:627-637`：`_clip_reason(limit=40)`，优先在标点断句，否则截断加「…」。

一个「引用最关键事实 + 说明缺什么」的 reason 很容易超过 40 字；截断后可能
只剩事实、没有缺口，模型自己也不知道被截了。
**建议**：二选一：
1. 放宽到 60 字，并更新测试/文档；
2. 输出契约加 `missing` 字段（如 `{"option": "...", "reason": "...",
   "missing": "底池未读全"}`），`reason` 仍 40 字。

### P1-10 「不是对加注范围」的权益口径，在全下局面与范围段矛盾

`metrics.py:8` 和 `strength.py:157` 都写「这是对当前/跟注范围的估计，
不是对加注范围」。但在对手全下的局面，`ranges.py:259-285` 明明给出了
`BB 转牌全下 ≈22.9%` 的范围，权益就是对这个全下范围算的。渲染的
HU 全下局面：

```
范围：BB 转牌全下 ≈22.9%
对当前范围权益：76%（…这是对当前/跟注范围的估计，不是对加注范围）
```

一个说「不是对加注范围」，一个说「范围就是全下」。这不是措辞小问题：
模型会低估这个权益的针对性。
**建议**：改成「对**当前建模范围**（可能是跟注/下注/加注范围；未建模的
对手按随机牌计入）的估计；不是对**未建模的**加注范围」。如果 `edge.jam`
为真，直接写「这是对全下范围的权益」。

### P1-11 `all-in` 标签的金额与实际推进的筹码不一致

`poker_ocr/options.py:126-129` 用 `all_in_amount = effective` 渲染「全下 18BB」，

所以 P0-1/P0-8 这类叠加冲突不会被测试抓到。
**建议**：加参数化矩阵测试，断言禁止短语对不共存（见 §五.6）。

## 五、优化建议

### 5.1 先做场景仲裁表（P0-1 的解法）

不需要一次写得很复杂，但必须有一个**可执行的优先级**。下面是一张可讨论
的草案；关键是选一个，而不是继续让五段并列：

| 组合 | 谁优先 | 例外/写法 |
|---|---|---|
| 短码 + 单挑 | 短码只约束**翻前**；翻后按 SPR/人数 | 翻后不写「优先 all-in 或弃牌」 |
| 短码 + 听牌 | 短码的「即时赔率」优先 | 不写「隐含赔率」；或写「短码下隐含赔率按 0 算」 |
| 短码 + 河牌 | 河牌的「按赔率+范围，不默认弃」优先 | 短码只保留「后手少，别假设中牌后还能收钱」 |
| 多人池 + 河牌 | 人数优先；无位置强价值仍可下注 | 多人池段加「两对+ 的价值下注不受『默认控池』限制」 |
| 多人池 + 听牌 | 人数优先；强听只在有弃牌率时半诈唬 | 听牌段加「多人池默认过牌」已覆盖 |
| 单挑 + 听牌 | 位置优先；OOP 纯听牌默认过牌，强听可半诈唬 | 单挑段加「听牌按听牌段，不按『主动定义底池』」 |
| 河牌 + 听牌 | 河牌优先；听牌段不出现 | `draw_section` 加 `if street == RIVER: return None` |

实现方式二选一：

- 在 `scenario.py` 顶部写 `SCENARIO_PRECEDENCE`，`build_system` 只渲染
  「最高优先级」的段 + 兼容段；或
- 保留五段，但每段开头写「本段不覆盖 X；冲突时按 Y」，并在
  `tests/test_advice.py` 里断言。

### 5.2 统一术语表（P0-2/P1-1/P1-2/P1-5）

建议把下面这张表放进 `shared/labels.py` 的 docstring 或
`docs/提示词模块拆分-2026-11-03.md`，所有模板引用同一组词：

| 词 | 定义 | 来源 |
|---|---|---|
| 后手 | 剩余筹码，不含本街已下注 | `snap.hero_stack` |
| 本手总筹码 | 后手 + 本街已下注 | `_hero_total_stack` |
| 有效筹码 | min(Hero 总筹码, 对手总筹码) | `_effective_stack` |
| 可玩深度 | min(我的后手, 最深未弃牌对手的后手) | `_playable_depth` |
| 身后 | 翻后座位顺序在 Hero 之后 | `_after_hero` |
| 本轮还要响应 | 行动顺序上 Hero 之后，或下注未跟到 | `behind_opponents` |
| 多人池 | **二选一**：3+ 或 4+ | 不要两套 |
| SPR 低 | **二选一**：<3 或 ≤3 | 不要两套 |

### 5.3 事实/建议分层（P0-6/P1-7）

最小改动：

- 在 user 块里加 `## 程序建议（不是事实）`，把攻击、桌况读法、范围结论、
  翻前继续范围、combo draw、范围警告都移进去；`## 事实` 只留数字和动作线。
- 如果不想大搬家，至少给每句建议加 `[建议]` 前缀，并在 priority 里写
  「`[建议]` 不是事实，冲突时按 1–4；`[建议]` 之间按『更具体』优先」。
- 做一个 `resolve_cbet(sit)`：逐座位 xr/call/fold + 桌级 c-bet + 攻击块
  → 一条结论；画像段只留数据，不再给动作。
- 删掉「最后读到裁决」的排版假设；如果保留攻击块在最后，块首写
  「以下是程序建议，与画像冲突时以画像为准」。

### 5.4 契约修正（P0-4/P0-7/P1-8/P1-9/P1-11）

- `call` 映射：把「只用于 SB 补盲/BB 过牌/limp 例外」限定到「无人入池」；
  另写「面对加注：call=跟注，raise-3x/4x=再加注」。
- 硬缺口：输出 `硬缺口：…` / `范围缺口：…` 两类标签；`HARD_GAP_KINDS`
  与 `output.py` 共用。
- 行动线：`（无行动）` → `（未记录到行动）`；有底池变化时补「本街底池 X→Y」。
- `reason`：40 → 60，或加 `missing` 字段。
- `all-in`：一个 id、一个有效金额；raise 封顶到全下时合并。
- `confidence`：如果下游不用，删掉或改成「可选，0–1，仅审计」；不要给
  模型一个不影响动作的字段。

### 5.5 去重（P2-1）

给每个事实指定唯一 owner：

| 事实 | owner |
|---|---|
| 底池/需跟/可争夺底池 | `situation` + `price`（只写一次） |
| 有效筹码/可玩深度/SPR | `geometry` |
| 权益/落后/公平份额 | `strength`（炸弹池只写结构） |
| 范围/宽度/封顶 | `ranges` |
| 桌况统计 | `table_stats` |
| 建议 | `## 程序建议` |

同一条事实如果在两个段都出现，后出现的段只写「见上」或删掉。

### 5.6 测试计划（P2-8）

新增参数化用例（可直接用 `make_point()`）：

| 用例 | 断言 |
|---|---|
| 18BB HU OOP 同花听 | system 不出现「优先 all-in 或弃牌」+「下注或过牌-加注」+「无位置默认过牌」三句无仲裁并列 |
| 18BB 听牌 | 不出现「只按即时赔率」+「用隐含赔率」并列 |
| 18BB 河牌面对加注 | 不出现「优先弃牌」+「不默认弃」并列 |
| 4 人河牌 OOP 两对 | 不出现「无位置默认过牌控池」+「价值下注」无例外并列 |
| HU 对手全下 | 不出现「让对手继续开火」「仍可再行动」 |
| 河牌面对全下无范围 | 出现「范围不可用」，且 system 不无条件说「按范围判断」 |
| 4-bet 池 | 「翻前形态」不是「3-bet」；选项不出现 4-bet/5-bet 混写 |
| 行动线缺失但底池变化 | 不出现「（无行动）」 |
| 后手 18 + 本街 1 | 全 prompt 只有一个「后手」数值，或两个词明确区分 |
| 4-bet 池全下 | 只有一条全下选项，金额一致 |

另外保留现有 `len(system) < 6000` 的防膨胀闸；不要用「加规则」解决冲突，
优先删/合并。

### 5.7 版本与回归

按 `prompt/version.py` 的约定，改文本必须：

1. bump `PROMPT_VERSION`（例如 `lean-zh-2026-11-04.1`）；
2. bump `replay-console/replay/versioning.py` 的 `CURRENT_ADVICE_VERSION`；
3. 更新 `replay-console/tests/test_prompt_golden.py` 的
   `EXPECTED_ADVICE_VERSION` / `EXPECTED_PROMPT_HASH`；
4. 同步 README 与 `docs/live-stream.md` 的版本号。

建议先做 P0-1~P0-5（事实/契约，低争议），再做 P0-6~P0-9（建议/边界，
需要产品拍板），最后做 P2 去重。不要在同一版里既改场景仲裁又改建议分层，
否则 A/B 归因不了。

## 七、哪些地方已经好了

避免只列问题，下面这些是这一版明显优于 2026-11-01 的地方，应该保留：

- 事实全部由程序算：`pot_math` 统一有效筹码/SPR/赔率；`ground_truth` 统一

- 场景段拆文件后，冲突已经可以被逐段测试；本轮找到的问题大多可以定位到
  一个函数/一行文案，不需要再读 5000 行。
- `system` 的 6000 字回归闸、`PROMPT_VERSION`/golden hash、prompt 捕获
  字段都在，改完可以复现「模型当时看到了什么」。
