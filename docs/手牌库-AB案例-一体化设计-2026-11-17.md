# 手牌库 · 场景期望 · 案例评分 一体化设计

日期：2026-11-17　状态：**待评审**（评审通过后按 §11 分期实施）
范围：`poker-ocr`（建议生成）+ `replay-console`（手牌库/重跑/评分）。`call-back`（复盘 app）**代码与 UI 不动**，只读。
本文取代 `docs/手牌库-自动沉淀与AB复盘-设计.md` 中"手牌集 + 实验"的部分；`docs/AB测试-手牌集.md` 的 23 条用例转为种子数据。

## 0. 这一版要解决什么

一句话：**手牌只有一份身份，好坏只有一个定义——"实际建议"离"我期望的建议"有多远，并按局面类型告诉你偏在哪。**

现状的五个断点（都已核对代码/数据）：

| # | 断点 | 证据 |
|---|---|---|
| 1 | 三套手牌身份，互不引用 | `review_hands` 自增 id；`replay_imported_hands` 从 1e12 起（`replay/migrations/002_imported_hands.sql`）；同内容手牌只按 `fingerprint` 去重**不合并**（`replay/service.py:_duplicate_groups`） |
| 2 | 两套 A/B 并行，语义不同 | `replay_experiments`（`007_experiments.sql`）vs 脚本 `tools/ab_set.json`（23 条，`expect=cross_down/stay_above`） |
| 3 | 期望挂在"手"上，到不了"决策点" | `replay_hand_set_items.expect_json`（`009_hand_sets.sql`）一手一条，只能写 option/尺寸/理由关键词 |
| 4 | 没有"期望 vs 实际"评分 | 只有 `replay/flags.py` 的启发式深挖分（排序用）和 `tools/advice_scorecard.py` 的动作占比 vs **单点**目标（40% / 60%） |
| 5 | 分桶维度已算好，但没有聚合 | `replay/decisions.py:47` 的 `DecisionPoint` 已带 texture / hand_strength / 位置 / 池型 / SPR，只缺一张按桶聚合的表 |

数据量（决定"重构代价低"这个前提）：`replay_imported_hands` 1139 手、`replay_decisions` 1443 点、`replay_live_advices` 1331 条 / 844 手、`replay_experiments` 1、`replay_hand_sets` 1、`review_hands` 52 手。

**一个纠正**：复盘库与控制台用的是**同一个 MySQL 实例**（`replay/config.py` 文件头第 4 条：复用 `call-back/.env` 的 `DB_*`）。所以"打通复盘"不是跨库拉取，而是**同库物化**——`review_hands` 就在眼前，`replay/repository.py:71` 一直在直接查它。§10 的同步步骤因此没有网络依赖，也没有凭据问题。

## 1. 已定的决定

| # | 决定 | 理由（简） |
|---|---|---|
| D1 | 复盘只读、不改；本期只评 live 建议（有 `option_id` 那套） | 复盘 app 的 AI 教练输出 `actionAdvice`，没有 option 概念；改它会把范围撑破 |
| D2 | 新建 canonical 手牌 + 决策点，多来源**并列保存**，`content_group` 归组，案例只挂 canonical id | 三源字段可信度不同，不该互相覆盖；打通要在数据模型上做 |
| D3 | 在 `replay-console`（:8010）原地演进 | runner / 版本 / prompt 快照 / timeline 都在，数据量小 |
| D4 | 案例单位 = **决策点**；手牌只是容器 | 期望天然落在"第几街第几个动作" |
| D5 | 先做"期望 vs 实际"评分，版本 A/B 后做 | 后者是前者的两列分数 |
| D6 | 期望 = 结构化硬约束 + 自由文本要点；机器判 + LLM 判 + 人可复核 | 硬约束可回归，自由文本能表达"依据要像我的思路" |
| D7 | 期望分**两层**：场景期望（主，带频率） + 实例案例（可覆盖） | "前位顶对过牌保范围"是一类局面的话，不是一手牌的话 |
| D8 | 分桶词表用教练 9 档 + 现有质地/位置/画像 | 判"符合期望"必须用模型提示词里看到的词 |
| D9 | 允许构造假设手牌（`source='synthetic'`），同等评分 | 河牌只有 19 个决策点，稀有线靠真实数据覆盖不到 |
| D10 | 一次运行 = 一个版本 × 冻结案例集，出**绝对分**；baseline 可选 | 回归不需要每次跑两臂 |
| D11 | 新表并存 + 一次性回填，旧表只读；`ab_set.json` 23 条转种子 | 那是唯一带人工期望的资产 |
| D12 | 频率只算案例集内同桶实例；n<15 不计分只显示区间 | 存档是旧版本 + 记录有选择偏差 |
| D13 | 自由文本按"要点清单"逐条判，judge 与被测模型解耦、temp 0、版本化 | 能解释、能回归、能复核 |
| D14 | spec / 案例集 / 案例 / 建议版本四者各自版本化，run 记四个版本号 | 防止"分数不可比但看起来可比" |
| D15 | 同一手牌靠"底牌 + 公共牌 + 时间窗"近似匹配归组，冲突人工确认 | OCR 与人工记录行动线常不一致，精确哈希配不上 |
| D16 | 权重 35/15/30/15/5，硬失败压到 ≤40，及格线 60 | 动作与依据各占三成半 |
| D17 | 热点页只做报表 + 下钻 + 一键建期望；不做告警、不做 CI gate、不做 LLM 归纳（v2） | 先有语料再谈自动 |
| D18 | 七个桶维度拆列，其余 facts 存 JSON | 热点查询走索引 |
| D19 | 分期：地基（canonical + 回填 + 列表）→ 期望/案例/评分/偏差 → 版本对照 → 复盘详情打磨 | 案例不返工到旧 id 上 |

## 2. 术语（建议合并进 `GLOSSARY.md`）

| 词 | 定义 | 不要说什么 |
|---|---|---|
| **决策点** decision point | 一手牌里 hero 的一个待决策时刻：街 + 该街第几个动作（`street` + `seq`），附当时的快照 | 不要说"一手牌就是一个案例" |
| **场景期望** spot spec | 对**一类局面**（位置 × 手牌档 × 牌面质地 × 对手画像 的任意子集）的行为规范：允许/禁止动作、尺寸带、频率带、必须提到/禁止说到的要点。有版本，可冻结 | 不要与"实例案例"混用 |
| **实例案例** case | 一个具体决策点 + 它被评时所用的 spec（+ 可选覆盖）。案例属于某个案例集 | 不要叫"测试用例"，容易与 `ab_set.json` 的用例混淆 |
| **案例集** case set | 一组冻结的案例；评分运行的基本单位 | 不要叫"手牌集"（旧词，指一手一条） |
| **桶** bucket | 七个自动维度的任意组合：街 / 位置档 / 牌力档 / 牌面质地 / 池型 / 是否面对下注 / 对手画像 | 不要用"分类""类目" |
| **硬失败** hard fail | 不是"分低"，而是"这条建议不成立"：非法 option、捏造事实、违反禁令、回落 fallback、运行错误 | 不要与"低分"混为一谈 |
| **P0** | 案例优先级：必须通过的硬约束案例 | — |
| **覆盖率** coverage | 有多少个桶的样本数达到 n≥15（可计分的桶）/ 全部有 spec 的桶 | 不要用"案例数"冒充覆盖率 |
| **运行** run | 案例集某个版本 × 一组 spec 版本 × 一个建议版本 × 一个 judge 版本，跑一遍 | 不要叫"实验"（旧词，指 A/B 双臂） |

## 3. 数据模型

### 3.1 三层

```
replay_hand_sources (源记录)  ──┐
  review  : review_hands.<id>   │  N:1
  live    : 导入/live 手牌 id    ├──→ replay_canonical_hands (canonical id, content_group, 主来源)
  synthetic: 构造手牌           ┘             │ 1:N
                                              ↓
                                    replay_decisions (+canonical_id, +七个桶列)
                                              │ 1:N
                                              ↓
                     replay_cases (spec_id, priority) ──→ replay_case_sets
                                              │
                                              ↓
                     replay_runs → replay_run_items（建议 + 判定 + 分）
```

- **canonical id 独立命名空间**：从 2e12 起（1e12 已被导入占用，见 `002_imported_hands.sql` 的 `AUTO_INCREMENT`）。
- **多来源并列**：同一手牌在复盘与实时两边都有时，两条 `replay_hand_sources` 指向同一个 canonical id，各自保留原始 payload 引用，**不互相覆盖**。
- **决策点不重造**：`replay_decisions` 已经由 `analyze_hand()` 从两种来源统一重放（`replay/service.py:126`），直接复用，只补 `canonical_id` 与七个桶列。

### 3.3 七个桶维度的口径

| 维度 | 取值 | 来源 |
|---|---|---|
| `street` | preflop/flop/turn/river | 已有列 |
| `position_bucket` | EP(UTG/UTG+1/UTG+2) / MP(LJ/HJ) / LP(CO/BTN) / 盲注(SB/BB) / ? | `tools/advice_scorecard.py:60` 的 `POS_BUCKET`，抽到共享模块 |
| `hand_tier` | `STRONG_MADE/OVERPAIR/TPTK/TP_WEAK/MID_BOTTOM/STRONG_DRAW/WEAK_DRAW/AIR/BOARD_PLAY` | `poker_ocr/coach.py:426-435` 的 `tier`；**存英文常量**，展示层再翻译成"顶对强踢"等 |
| `board_texture` | 干燥 / 花面 / 顺面 / 花顺面 / 公对面 | `poker_ocr/ground_truth.py` 的 `board_texture()`；枚举见 `poker_ocr/situation.py:48` |
| `pot_type` | limped / single / 3bet+ / bomb / unknown | `tools/advice_scorecard.py:_pot_type` |
| `facing` | 0/1 | `to_call > 0` |
| `opponent_profile` | 紧弱 / 松弱 / 松凶 / 紧凶 / 未知 | `poker_ocr/opponent_profile` 的读牌；**取本街最后加注者**，无则"未知" |

前五个可由 `snapshot_json` 离线重算（回填脚本），后两个直接读快照。**不要**在查询时实时重算——那会把热点页变成 N 次重放。

`hand_tier` 存稳定键而不是中文标签：`coach.py` 的标签文案被 `replay/versioning.py` 的注释记录过多次调整（"顶对强踢 T→J"），存中文会让老 spec 在某次改文案后集体失配。

### 3.4 `content_group` 关联规则

1. 候选对：`hero_cards` 相同 **且** `board` 相同 **且** `|started_at 差| ≤ 30 分钟`；
2. 命中的源记录挂到同一 canonical id，`content_group = sha1(hero_cards|board|日期)`；
3. `primary_source` 默认 `review > live > synthetic`（人工记录优先）；
4. 自动关联存疑（如同一对出现 3 条以上、或起止时间跨越）→ 进"待确认"页，人工合并/拆分；
5. `merged_into` 只做软合并，被合并行的源记录整体改挂，**永不删除**。

```json
}
```

- `bucket` 的每个维度是**数组**，缺省 = 通配；维度之间是 AND，数组内部是 OR。
- **只取需要的维度**：强制全维度笛卡尔积的话，现有数据没有哪个桶能到 n≥15（9 档 × 5 质地 × 4 位置 × 4 画像 = 720 桶，1443 个决策点）。
- `required_points` 是"要点"，不是"必须出现的字串"——判定由 LLM 做语义命中（§7.1），`text` 只是给人看的。
- `sizing.unit` 支持两种：`pot_fraction`（占池比例）与 `bb`（本街加到多少 BB，与 `option_amount` 同口径，见 `AGENTS.md` 铁律）。`sizing` 可写成对象或数组：数组表示多条带**同时**约束（如"不超过 0.75 池且不超过 4BB"），`s_size` 取各带得分的最小值。`pot <= 0` 时池比例带不参与（fail open）。
- `freq` 可缺省；缺省时该 spec 只做实例判定，不参与频率统计。样本门槛 `FREQ_MIN_N = 15` 是**代码常量**，不写进 spec、不随 run 覆盖。

### 4.2 一个决策点匹配多个 spec 时

按"维度数最多"优先（更具体者胜），平手取最近创建的；案例创建时**显式写死**选中的 `spec_id`，运行不再动态匹配。这样加一个泛化 spec 不会悄悄改变已有案例的分数。

### 4.3 版本与冻结

- 每次编辑 = 新 `revision`，旧行不可变；`status` 由人显式置 `active`。
- 案例引用 `spec_id`；运行冻结 `spec_ids_json`。跨 revision 比较时 UI 必须提示"期望已变，只能比共同案例"。

## 5. 案例与案例集

- **建案例**：从手牌详情的决策点时间线点"建案例"→ 先按 §4.2 选 spec（默认最具体匹配）→ 存 `(case_set, canonical_id, street:seq, spec_id, priority)`。
- **批量**：手牌详情有"整手全建"；案例集有"按桶补样"——给定桶与目标 n，从存档里按时间倒序抽符合条件的决策点建成 draft 案例。
- **冻结**：`frozen_at` 一置，该 revision 的案例不允许增删；要改就升 revision 建新集。
- **P0 的判定标准**：写 spec 时勾"P0"，含义是"这条硬约束不许破"。

---

## 6. 运行

一次 run = `(case_set revision) × (spec revisions) × (version_id) × (judge_version) × (reconstruct_version)`，五个都在创建时冻结进 `config_snapshot`。

执行复用现有引擎：`replay/runner.py`（DB 队列 + 线程池）与 `replay/engine.py` 的 `execute_unit()`；建议生成仍走 `poker_ocr/advice.py:advise(prompt_override=...)`，prompt 从版本快照取，**不重新渲染**（与现有 A/B 一致，`baseline_prompt_mode=stored`）。

与旧链路的关系：

- 旧 `replay_jobs / replay_results` 保持不动（历史可追溯）；
- 新 run 只写 `replay_runs / replay_run_items`；
- 建议版本仍来自 `replay_versions`（模型 + 采样 + prompt 版本 + 重建版本的 `config_hash`），不新造版本概念。

## 7. 评分

### 7.1 单案例

```
可选维度 D = {action, size, reason, fact, stable}
权重 W = {action:35, size:15, reason:30, fact:15, stable:5}

s_action = 1 if 实际 kind ∈ allowed 且 kind ∉ forbidden else 0
s_size   = 1 若实际 kind ∉ {bet,raise,allin}（无需尺寸）
         = 1 若换算后落在带内（pot_fraction 用 option_amount/pot；bb 直接用 option_amount）
         = max(0, 1 - 距离/带宽) 若带外（带宽 = max-min；min==max 时用 0.1 兜底）
         = 多条带时取各带得分的最小值；pot<=0 时池比例带不参与
s_reason = 命中要点的加权和 / 要点总权重（要点为空时退化为"理由是否支持该动作"，0/1）
s_fact   = 1 - 错误事实项 / 引用事实项总数（引用 0 项时记 1）
s_stable = N 次重复的动作一致率（未抽样则不参与）

score = Σ W_d·s_d / Σ W_d   （d 只取可选维度；分母随可选维度变化，见 §7.4）
if hard_fail: score = min(score, 40)
```

### 7.2 硬失败（不进加权，直接封顶 40）

| 码 | 条件 |
|---|---|
| `HF_OPTION` | `option_id` 不在该决策点的 `options` 里 |
| `HF_HALLUCINATION` | 把模型当时实际看到的输入（`prompt_json.user`）里**完全没有的**具体事实当依据（如"对手 3bet 18%""他有两对"） |
| `HF_FORBIDDEN_ACTION` | 命中 `forbidden_actions` |
| `HF_FORBIDDEN_POINT` | 命中 `forbidden_points` |
| `HF_FALLBACK` | `source != 'model'`（引擎回落，等同没有建议） |
| `HF_ERROR` | 运行异常 |

划分边界（否则实现必然模糊）：**事实说错**（把 CO 说成 UTG、把 40BB 说成 20BB，即 judge 的 `contradicted`）= 扣 `s_fact`，不算硬失败；**事实无中生有**并被当作依据 = `HF_HALLUCINATION`。事实源是模型当时实际看到的 prompt 原文；结构化 `facts_json` 只用于 options / id 与结构参考，冲突以 prompt 为准。没有留存 prompt 时（`store_prompts=false` / 旧行 NULL）不出 `HF_HALLUCINATION`（fail open）。

`HF_*` 全部**纯自动判定，不设二次人工确认**。为了让自动判定可复核，每条硬失败必须把 evidence 落进 `judge_json`：`{引用的原句, 模型输入里缺失的事实项, 命中的禁令}`。要推翻它走 `replay_judge_overrides`（§3.2），原始判定不被覆盖，聚合时优先取人工结果。

### 7.3 聚合

| 指标 | 定义 |
|---|---|
| 总分 | 有效案例 `score` 的算术平均（0–100） |
| P0 通过率 | `P0 且 无硬失败 且 s_action=1` 的案例 / P0 案例数 |
| 覆盖率 | 达到 `FREQ_MIN_N`(固定 15) 的桶数 / 有 active spec 的桶数 |
| 频率达成率 | §7.5 |

### 7.4 稳定性采样

- 全量跑 1 次；**稳定性的样本固定为案例集里全部 `priority=0` 的案例**，对它们额外跑 2 次（共 3 次）。不随机抽——随机抽会让同一案例集两次运行的分不可比。
- 未采样的案例：`stable` 不参与，分母按剩余维度的权重和归一（即 `score = Σ W_d·s_d / Σ_{d≠stable} W_d`），不假设固定分母。

### 7.5 频率

- 样本 = **本次 run 内**、桶内所有案例的**首次**建议（不含重复采样，避免同一手牌被 3 次重复加权）。
- `obs = count(kind == freq.action) / n`。
- 达成：`min ≤ obs ≤ max` → 1；否则按 `max(0, 1 - 超出量 / 带宽)` 线性衰减。
- `n < 15`（`FREQ_MIN_N`，代码常量，不随 spec / run 覆盖）→ 不判定，标"样本不足"，不计入频率达成率。

### 7.6 置信区间

- 比例类（P0 通过率、硬失败率、频率）：Wilson 95% 区间；
- 均值分：正态近似 `mean ± 1.96·sd/√n`；
- 页面上 n、区间、口径永远一起出现——**没有区间的"偏差大"不算结论**。

## 8. 偏差热点

桶表列：`桶（维度组合）| n | 均分 | 硬失败率 | 实际频率 vs 目标带 | 与全局均分之差 | CI`。

排序严重度：

```
dev = spec 有 freq ? min(3, |obs - 带中点| / max(带宽/2, 0.02))
                   : min(3, (100 - mean) / 50)
severity = dev * sqrt(n)
```

下钻：点桶 → 该桶下的案例列表（低分 / 硬失败优先）→ 点条目看"期望 vs 实际建议 vs 判定逐项"→ 按钮"建/改 spec"（把该桶维度预填进新 spec）。

不做：阈值告警、CI 卡点、LLM 自动归纳（v2 再说，等有几十条 spec 语料）。

## 12. 风险与边界

| 风险 | 处理 |
|---|---|
| LLM judge 方差 | temp 0、要点清单化、10% 人工抽检；judge 版本进 run 冻结 |
| judge 与被测模型同源偏好 | judge 取**独立模型的最强档**（与被测模型不同 provider 或不同模型）；`judge_version` 写清模型名与 prompt 版本 |
| 成本 | 案例数 × 1 次 + P0 × 2 次；单次 run 的成本在创建页先估算并确认 |
| 构造手牌污染真实分布 | `is_synthetic=1`，所有"真实分布"统计默认排除；评分不排除 |
| `reconstruct_version` 漂移 | run 冻结 `reconstruct_version`；跨版本比较视为不同口径 |
| 词表漂移 | 桶维度存稳定键（`TP_WEAK` 等），展示层翻译 |
| 复盘库写入风险 | 只读账号 + 代码评审 + 第 1 期验收项 |

**不做**：改 `call-back`；评复盘 AI 教练；自动改 prompt；跨用户权限；CI gate。

## 13. 细节决定（2026-11-17 已定）

1. **尺寸单位**：`pot_fraction` 与 `bb` 都支持，按 spec 的 `sizing.unit` 判定；`sizing` 允许写数组做多条带同时约束（§4.1、§7.1）。实现时两套换算抽一个函数，别在 judge 与 runner 里各写一遍。
2. **judge 模型**：独立模型的最强档，与被测模型不同 provider 或不同模型；具体型号在实现时选定并写进 `judge_version`，**不在 spec 里**。
3. **幻觉判定**：纯自动，不做二次人工确认；但必须留 evidence（§7.2），人工推翻走 `replay_judge_overrides`。
4. **频率门槛**：`FREQ_MIN_N = 15` 固定，不做 per-spec / per-run 覆盖；桶到不了 15 就显示"样本不足"，靠补样解决而不是降门槛。

> 这四条落进代码时各自对应的常量/配置项：`SIZING_UNITS = {"pot_fraction", "bb"}`、`JUDGE_MODEL`（环境变量 + 版本快照）、`HF_EVIDENCE_REQUIRED = True`、`FREQ_MIN_N = 15`。
