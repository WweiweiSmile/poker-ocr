# 用 SpinGPT 两阶段流水线训一个 8B 德州顾问

> 面向本仓库（`poker-ocr`：9 人桌 1/2 带前注、屏幕 OCR、实时建议）。
> 参考：Maugin & Cazenave, *SpinGPT: A Large-Language-Model Approach to Playing Poker Correctly*,
> ACG 2025 / [arXiv:2509.22387](https://arxiv.org/abs/2509.22387)。

---

## 0. 先看结论

1. **流水线能照搬，数据不能。** 论文第一阶段是作者本人 2018–2020 年在 PartyPoker.fr 打
   €50/€100/€250 Spin & Go 的 **8,800 局、32 万决策**——私有数据，论文明确说不公开，
   只接受研究者申请。你手上是 `hands.json` 的 107 手，转出来 **91 条**可用决策。差三个数量级。
2. **这是两个游戏。** 论文是 3 人桌、25BB 起始、ICM 主导的 hyper-turbo；你是 9 人桌、
   100BB、cEV。论文自己就写了：SFT 模型在 200BB 下疯狂全下，得靠人工补丁（全下改 2/3 池）
   才打得过 Slumbot。直接抄配方，你会得到一个「25BB 全下机器」。
3. **真正值得抄的是三件事**：紧凑状态编码 + 闭集动作 token、LoRA SFT → 偏好对齐的两段式、
   tolerant accuracy / MAE 这套评估口径。
4. **你的任务比论文简单。** 金额由程序算好、选项是 7 个 id 的闭集，模型只做选择题。
   论文那个最丢人的失败模式（把 `5.11` 当成大于 `5.2` 的数值幻觉、1.4% 非法动作）
   在你的架构里天然不存在——别把这条优势丢掉。
5. **数据现实排序**：求解器自建 > 强模型拒绝采样蒸馏 > 公开手牌库 > 买手牌。
   公开数据里唯一「全底牌 + 高水平」的是 Pluribus 那 1 万局，但它是 6 人桌，补得了翻后、补不了你的 9 人桌翻前。

## 1. 论文做了什么（可直接对照的配方）

| | 内容 |
|---|---|
| 基座 | Llama-3.1-8B-Instruct |
| 阶段 1 | SFT，32 万决策 / 8,800 局，真人职业玩家历史 |
| 阶段 2 | ORPO 偏好对齐，27 万条 InstaGTO 求解器手牌 + 5 万条真人手牌混训 = 32 万 |
| 正样本 | 求解器 argmax-EV 动作 |
| 编码 | 单行紧凑文本 `pos:H=BTN stacks:H=29.3,BB=1.7 hand:TsQs \| pre:H r2,SB c,BB f \| ...`，输出 `r6.5` |
| SFT 超参 | LoRA r=8 / α=16 / 无 dropout / 4 epoch / seq 128 / lr 5e-5 cosine / 约 1,000 万可训参数 |
| ORPO 超参 | QLoRA 4bit NF4 双量化 / β=0.1 / 2 epoch / seq 128 / lr 2e-5 / 优化器 BF16 |
| 算力 | 各 10 小时，单卡 A100 40GB |
| 结果 | 对真人 80% 精确 / 84% 容忍；对求解器 72% 精确 / 78% 容忍；对 Slumbot +13.4±12.9 BB/100（3 万手） |
| 开源 | **权重和数据都不放**，理由是怕被做成违反平台条款的 bot |

两个数字要记住：**78% 容忍准确率**意味着对着求解器仍有 22% 的决策不一致；
**13.4 ± 12.9** 的置信区间下界接近 0.5 BB/100——这活儿的天花板没有宣传得那么高。

## 2. 你和它的四个硬差异

| 维度 | SpinGPT | 你 |
|---|---|---|
| 人数 / 深度 | 3 人，25BB 起，随时变 | 9 人，100BB，带 0.5 前注 |
| 目标函数 | ICM（筹码非线性） | cEV（筹码线性） |
| 动作空间 | 自由生成金额 token | 7 个闭集 id（`fold`/`call`/`raise-1/3`…`raise-1.2`） |
| 输入 | 裸行动线，模型自己算赔率 | 事实层已给胜率、赔率、牌型排名、每个选项的金额 |

第 4 行是关键：**你的模型不需要会算数**。这让 8B 的数据效率远高于论文，
也意味着训练集里必须保留这些计算事实，否则等于让模型去学它推理时不具备的能力。

## 3. 改造后的两阶段

### 阶段 A：行为克隆（SFT）

- 输入 = 线上 `advice.build_messages()` 产出的 system + facts，**逐字节一致**；
- 输出 = `{"option": "<id>"}`，默认不带理由（带上会多 30+ token，延迟翻倍）；
- 数据配比建议：

| 来源 | 占比 | 作用 |
|---|---|---|
| 求解器标签（单挑翻后） | 40% | 策略正确性 |
| 教师拒绝采样（你的分布） | 40% | 分布对齐、9 人桌翻前 |
| 真人实战（自有 + 公开） | 20% | 行动线自然度、长尾 |

### 阶段 B：偏好对齐（ORPO / DPO）

- `chosen` = 求解器 argmax-EV；`rejected` = 同 spot 下 EV 差 ≥ 0.5BB 的次优动作；
- 必须混 20–30% 阶段 A 数据（论文混 16%，但你的分布更窄，混少了会忘）；
- 没有求解器就先别做阶段 B——用规则当 verifier 造出来的 pair 只会把规则学进权重。

## 4. 数据从哪拿（核心）

### 4.1 你自己的（已有，但是种子不是主粮）

| 文件 | 内容 | 量 |
|---|---|---|
| `hands.json` | 107 手完整牌局，含底牌、行动线、结果 | 101 个可比决策点（复盘口径）→ 91 条能当训练样本（跳过 8 条陈旧帧 + 10 条标签已被现行选项生成器淘汰） |
| `logs/live.states.jsonl` | 612 帧状态 | 用来采样「你实际遇到的 spot 分布」，无标签 |
| `hands_review.csv` | 每手盈亏 | 给蒸馏做加权（输的牌面多采） |

用法：**eval + spot 采样器 + 种子**，不是训练主粮。91 条训 8B 只会背下来。

### 4.2 求解器自建（主力，唯一能规模化产出「正确答案」的路）

- 工具：[TexasSolver](https://github.com/bupticybee/TexasSolver)（开源、免费）；
  商用可选 PioSolver / GTO+ / 论文用的 InstaGTO。
- **只能解单挑（HU）翻后**——上面这几个都是两人求解器，别指望它们处理 3 人以上底池。
  3-way 要用 GTO Wizard / MonkerSolver / InstaGTO 这类多路引擎，成本高一个量级。
  所以 3 人以上底池这段交给规则 + 教师（你的 `advice.py` 里 `value_directive`
  已经在干这事），别硬编求解器标签。
- **一次求解 ≠ 一条标签。** 一次求解产出整棵树里所有手牌组合的策略，
  通常能切出 200–2,000 条决策标签。按「决策数」估算成本会高估一到两个数量级，
  真正要买的是**唯一配置数**（牌面 × SPR × 行动线），不是 spot 数。
- 产 data 的流程：
  1. 从你的日志里抽 spot 类型（位置、底池、SPR、牌面纹理、人数）→ 采样 5–10 万个；
  2. 每个 spot 建一棵小树（每条街 2–3 个尺度，别用全树）；
  3. 跑求解器 → 取每个决策点的动作频率与各动作 EV；
  4. **ORPO 用**：`argmax EV` 当 chosen，`EV 差 ≥ 0.5BB` 的当 rejected；
  5. **SFT 用**：按动作频率采样，而不是只取 argmax——只学 argmax 会得到确定性策略，
     永远不会诈唬，被会弃牌的对手打爆。
- 算力账：官方跑分（Qs Jh 2h，收敛到 <0.2% exploitability）GPU 版 24.4 秒、PioSolver 86.1 秒；
  训练标签不需要这个精度，1–2% exploitability 大约快 3–5 倍，单次 5–8 秒。
  说明：那个跑分没标硬件，按 4090 量级估；5090 大约快 1.3–1.5 倍（CFR 吃显存带宽，
  不是纯 FP32）。真正卡人的是 **GPU 版目前只发 Windows**，无头 Linux 流水线要么用 Wine，
  要么退回 CPU 版 console_solver（同一棵树 CPU 172 秒，慢 7 倍以上）。

### 4.3 公开手牌库

| 来源 | 有什么 | 能用吗 |
|---|---|---|
| **Pluribus**（CMU/Facebook，1 万局 6-max 100BB，全底牌） | bot 对职业选手，水平高、行动线完整 | ✅ 翻后主力补充；但 6 人桌，翻前结构与你不同。解析器：[pluribus-hand-parser](https://github.com/VitamintK/pluribus-hand-parser) |
| PokerGPT 的数据（NL5 观众视角） | 量大，但底牌经常缺失、对手是鱼 | ⚠️ 只能当格式/规则语料。论文专门批评过它 |
| Kaggle 各类 PokerStars HH | 千万手，但大多无底牌 | ❌ 无标签 |
| WSOP / 直播手牌 | 有底牌，几百手 | ⚠️ 展示性对局，尺度不真实 |

### 4.4 强模型拒绝采样（最快冷启动，1 天能出 1 万条）

你已经有现成的重放器（`tools/replay_live_decisions.py --model --json`），
把它改成批量：

1. 从日志 + 合成的牌面里采样 2–5 万个 spot；
2. 用 `deepseek-v4-pro`（比 flash 强一档）打标，temperature 调低；
3. **用程序当 verifier 过滤**：违反 RFI 表、违反 `value_directive`、
   有赔率却弃牌、范围内却弃牌 —— 这些判据你仓库里全都有；
4. 只留通过的，按输出长度和理由质量再筛一遍。

上限就是教师，但它是唯一能覆盖「你摄像头真正见到的桌子」的数据。
成本量级：2.5 万 spot × 2k token ≈ 5,000 万 token，几百块人民币。

### 4.5 买手牌 / 抓平台数据（不建议）

多数平台 ToS 明确禁止抓取与转售，GTO Wizard 也禁止批量导出。
论文拒绝开源权重就是这个原因。真要走这条路，找数据方谈书面授权，别用爬的。

## 5. 操作步骤（0 → 7）

### Step 0　冻结契约（半天，最重要）

训练和推理共用同一份 system + facts 渲染。现在的入口已经是对的：
`advice.build_messages(sit, "lean")`。**不要在训练集里另写一套 prompt**，
否则模型学的是另一个任务。

### Step 1　先把 eval 做出来（别放到最后）

```bash
# 101 个可比决策点的基线（当前代码 + 当前模型）
.venv/bin/python tools/replay_live_decisions.py --json baseline.json
# 真跑模型对比
.venv/bin/python tools/replay_live_decisions.py --model --model-name deepseek-v4-pro --json pro.json
```

再攒一个 **2,000 条的求解器 holdout**（和训练集按牌面去重），
这是唯一能判断「有没有真的变强」的尺子。101 个点太少，噪声比信号大。

### Step 2　跑通链路（1 天）

```bash
.venv/bin/python tools/build_sft_dataset.py --out data/sft
llamafactory-cli train config/llamafactory/sft_lora.yaml
```

91 条、4 epoch，**目标不是效果好，是 loss 能降到 0.2 以下、训练集能 100% 复现**。
跑通了再谈数据量，顺序反了会浪费一周。
（要连理由一起学、给复盘用，加 `--with-reason`；线上实时建议不要带，多 30 个 token 就是多 300ms。）

### Step 3　求解器数据（1–2 周，真正的瓶颈）

按 4.2 写 `tools/solver_spots.py`：抽 spot → 调求解器 → 解析 → 写 `data/orpo/`。
先做 500 个 spot 验证解析正确（用已知的简单局面手算对一遍），再放量。

### Step 4　教师扩量（2–3 天）

按 4.4 把 `replay_live_decisions.py` 的 `--model` 分支抽成 `tools/label_spots.py`，
输出与 Step 2 同格式，直接拼进 `data/sft/train.json`。

### Step 5　SFT 正式训练

```bash
# 单卡 A100 40G，10 万条 × 2 epoch 约 15–25 小时
llamafactory-cli train config/llamafactory/sft_lora.yaml
```

超参就用 yaml 里的（对齐论文），唯一偏离是把 seq 从 128 提到 2048——
你的事实层（system 5.4k 字符 + facts 1.3k 字符）比论文的单行编码长一个数量级。

### Step 6　ORPO

数据齐了再跑，`config/llamafactory/orpo_qlora.yaml`，24G 卡也能跑（QLoRA 4bit）。

### Step 7　上线

```bash
# 1) 合并 LoRA（export 不吃训练 yaml，参数要显式给）
llamafactory-cli export \
  --model_name_or_path Qwen/Qwen3-8B \
  --adapter_name_or_path saves/poker-8b/sft \
  --template qwen3 --finetuning_type lora \
  --export_dir saves/poker-8b/sft-merged

# 2) 起服务
vllm serve saves/poker-8b/sft-merged --served-model-name poker-8b \
  --max-model-len 4096 --gpu-memory-utilization 0.9
```

**必须开 guided decoding**，把当前这一手的合法 option id 作为 enum 传进去：

```python
guided_json = {"type": "object",
               "properties": {"option": {"enum": [o.id for o in sit.options]}},
               "required": ["option"]}
```

这一步把非法动作率从论文的 1.4% 直接压到 0，而且不用改模型。

## 6. 训练配置

| 文件 | 用途 |
|---|---|
| [`config/llamafactory/sft_lora.yaml`](../config/llamafactory/sft_lora.yaml) | 阶段 A，LoRA r=8 / α=16 / 4 epoch / lr 5e-5 |
| [`config/llamafactory/orpo_qlora.yaml`](../config/llamafactory/orpo_qlora.yaml) | 阶段 B，QLoRA 4bit / β=0.1 / 2 epoch / lr 2e-5 |
| [`tools/build_sft_dataset.py`](../tools/build_sft_dataset.py) | 现有数据 → LLaMA-Factory 数据集 |
| `data/sft/` | `train.json` / `eval.json` / `system.txt` / `dataset_info.json`；**当前是旧英文 prompt 的 stale 数据，见 `data/sft/STALE.md`，不要直接训练** |

基座选 **Qwen3-8B**（比 Llama-3.1-8B 新、中文好、工具链成熟）；
要严格复现论文就换 `meta-llama/Llama-3.1-8B-Instruct` + `template: llama3`。

旧 `system.txt` 是 5,371 字符的英文 prompt；中文 lean 的 `SYSTEM_ZH` 约 900 字符。
训练前必须用 `tools/build_sft_dataset.py` 重新生成，不能沿用旧文件。LLaMA-Factory 的 `dataset_info.json` **没有**
全局 `default_system` 这种键（翻过 `parser.py` / `converter.py`，只认 `columns.system`），
所以每条样本各带一份，10 万条会到 500MB 量级——那时候把 `train.json` 换成 `train.parquet`，
列式字典编码会把这段重复文本压掉，加载也快一个数量级。

## 7. 怎么判断有没有变强

| 指标 | 门槛 | 怎么测 |
|---|---|---|
| 求解器容忍准确率 | ≥ 70%（论文 78%） | 2,000 条 holdout，动作类型对 + 尺寸 ±0.5BB |
| 规则违规率 | ≤ 2/101 | `replay_live_decisions.py` + 你现有的违规判据 |
| 非法动作率 | 0 | guided decoding 下必须是 0 |
| 输出长度 | ≤ 12 token | 只输出 option，不带理由 |
| p50 延迟 | ≤ 400ms | 自建 vLLM，含网络 |
| 实战 | 先影子模式 200 手 | 只记录不下注，人工比对 |

现在的线上基线是 **101 个决策 1 个违规、p50 962ms**（见 `docs/模型对比-flash-vs-pro.md`）。
先想清楚你要赢哪一项——见下一节。

---

## 8. 这笔投入值不值

**如果瓶颈是延迟 / 成本 / 离线可用**：值得。8B + 短输出 + vLLM，
p50 预计 200–400ms，比现在的 962ms 快 2–4 倍，单次成本趋近于 0，不依赖第三方 API。

**如果瓶颈是决策质量**：先别训。你现在的 flash 已经是 1/101 违规，
一个 SFT 出来的 8B 在没见过的牌面上大概率不如 v4-pro——蒸馏的上限就是教师。
这种情况下性价比更高的是：**求解器查表 + RAG**（论文 Future Work 自己也这么说），
以及把 `preflop_ranges.py` / `value_directive` 这类规则继续做厚。

最理性的组合是**混合推理**：8B 处理 90% 的常规局面（快、免费），
规则判为「边缘 / 大池 / 多路」的 10% 升级给大模型。这样既拿到延迟，又不丢质量。

---

## 9. 七个坑

1. **拿 91 条训 8B**：会得到一台复读机，eval 上还很好看（同一手牌的其它街泄漏进来了）。
   切分必须按 `hand_id`，`build_sft_dataset.py` 已经这么做了。
2. **训练集 prompt 和线上不一致**：改了 `advice.py` 的 system 就必须重导数据集。
   最省事的做法是每次训练前重跑 `build_sft_dataset.py`，别存旧的。
3. **只取 argmax 当标签**：模型会学成从不诈唬的确定性策略，被会弃牌的对手打爆。
   求解器数据要按动作频率采样。
4. **灾难性遗忘**：只训求解器数据会让模型忘掉 9 人桌翻前。混 20–30% 阶段 A 数据。
5. **9 人桌多路翻后没有 ground truth**：4 人以上底池，求解器给不出可信解。
   用规则兜底，别硬编标签——错的标签比没有标签更糟。
6. **标签来自 deepseek-flash 自己的决定**：它的错误会被一起学走。
   这就是为什么 4.4 要用 v4-pro + verifier，而不是直接拿现在的 `advice` 记录。
7. **合规**：实时辅助在多数平台违反 ToS，论文也因此拒绝开源权重。自己清楚边界。
