## 1. 现状：一个桶管所有人

### 1.1 表在哪、怎么被消费

| 位置 | 内容 |
|---|---|
| `poker_ocr/ranges.py:262` | `"COLD_CALL_IP": (...)`，29 个 token，展开成 52 个 169 键 |
| `poker_ocr/ranges.py:269` | `"COLD_CALL_OOP": (...)`，展开成 45 个 169 键 |
| `poker_ocr/ranges.py:380-386` | `get()` 的 `COLD_CALL_` 分支 |

```python
if upper.startswith("COLD_CALL_"):
    # COLD_CALL_<IP|OOP>_vs_<bucket>
    head = upper.split("_VS_", 1)[0]
    ip_oop = head.replace("COLD_CALL_", "", 1).strip("_")
    base = "COLD_CALL_IP" if ip_oop == "IP" else "COLD_CALL_OOP"
    return _range_from_rule(rid, base)
```

`head = upper.split("_VS_", 1)[0]` 把 `_vs_<开池位置>` **整段丢掉**：`_vs_EP` / `_vs_MP` /
`_vs_LP` / `_vs_SB` 拿到的是同一个 `base`。实测（`ranges.get` 逐 id 打印）：

| id | combo | 宽度 | source |
|---|---|---|---|
| `COLD_CALL_IP_vs_EP` / `_vs_MP` / `_vs_LP` / `_vs_SB` | 268 | **20.21%** | `rules:cold_call_ip` |
| `COLD_CALL_OOP_vs_EP` / `_vs_MP` / `_vs_LP` / `_vs_SB` | 222 | **16.74%** | `rules:cold_call_oop` |

也就是说**两个轴一起缺失**：位置轴存在（id 里有 `_vs_`）但被丢弃，人数轴根本不存在。
`docs/手牌范围基准-实现方案.md:196` 当初设计的是 6 张位置桶表
（`COLD_CALL_<IP/OOP>_vs_<EP/MP/LP>`），落地时塌成 2 张。

生产里有**四个**消费点，都吃这个 id：

| # | 位置 | 用途 |
|---|---|---|
| 1 | `poker_ocr/hand_vs_ranges.py:713` `prior = ranges.get(spec.prior_id)` | 翻牌后对手范围（`field_ranges` → 先验 → 事件收窄 → `_monte_carlo`），冷跟先验的主战场 |
| 2 | `poker_ocr/field_ranges.py:183-185` | 生成 id：`f"COLD_CALL_{'IP' if ip else 'OOP'}_vs_{bucket(opener_pos)}"` |
| 3 | `poker_ocr/prompt/user/preflop.py:218` | hero 自己面对单加注时的「冷跟范围」文案与判定 |
| 4 | `poker_ocr/prompt/user/preflop.py:227` | hero 是 BB 且 `multiway` 时，从 `BB_DEF_*` 切到 `COLD_CALL_OOP_*`（「多人池紧防守范围」） |

第 4 点是本文最重要的现状事实：**代码里已经有一个二值的人数开关**。
`poker_ocr/prompt/user/preflop.py:170` `multiway = bool(callers or limpers or behind)`，
`:224` `elif hero_pos == BB and multiway:` 才切表。也就是说「人多要收紧」这个方向，
代码是认的——只是①只认 0/1 两档，②只在 BB 一个座位上生效，③不在翻牌后的对手范围
（消费点 1）里生效。本草案就是把这个已有开关从「二值 × 1 个座位」变成
「三档 × 所有冷跟座位」。

## 2. 分桶方案：2 / 3 / 4+ 人池

### 2.1 档位定义（可机械判定，不需要猜）

对一个冷跟座位 S：

```
n_way(S) = 1（开池者）
         + S 之前（不含 S）所有自愿进池的翻前 call / limp / all-in-call 数
         + 1（S 自己）
tier = min(4, max(2, n_way))
```

数据来源：`snap.streets` 里 `street == "preflop"` 的动作序列（`ActionRecord`，
hero 用 `__hero__` 占位、按 `is_hero` 区分）。这组口径与代码里已有的
`tight_reasons`（`poker_ocr/prompt/user/preflop.py:160-169`：`limpers` / `callers` / `behind`）
同一套词汇，只是把 `behind`（还没响应的人）排除在外——只数**已经确定在池里**的人。

**不计 `behind`** 是刻意的：`behind` 是「可能会跟」的估计，把它算进档位等于在猜。
`behind` 继续留在文案与 `tight_reasons` 里（现状已这么做）。

### 2.3 删什么、留什么（三档共用一条规则）

**删**：

- 被统治的弱同花宽张 `K7s–K9s / Q7s–Q9s / J7s–J8s / T7s–T8s`（tier3 起）；
- 一 / 二隔张 `97s / 86s / 75s`：**IP 只在 tier4 删**（tier3 留，多人池要靠隐含赔率），
  **OOP 从 tier3 就删**（没位置，隔张的兑现率更低）；
- 非同花宽张：IP 现状只有 `KQo / KJo / QJo / JTo / T9o` 五张，tier3 删 `QJo / JTo`，
  tier4 再删 `KJo`（**保留 `T9o`**：最便宜、还能成顺的一张）；OOP 现状只有
  `KQo / KJo / QJo`，tier3 删 `QJo`，tier4 再删 `KJo`；
- OOP 的弱 A 同花 `A6s–A9s`（只在 tier4 删）。

**留**：小对子（多人池隐含赔率上升）、同花 A、同花连张（54s–JTs）、`KQo / KJo` 这类
够硬的非同花大牌。

一句话：**收紧靠换形状，不靠等比缩小**。等比缩小会把 22–66 一起砍掉，那是把
「多人池该多便宜看翻牌」的常识反过来了。

## 4. 为什么按人数分桶，不按位置分桶

### 4.1 三个正面理由

1. **位置轴今天等于没生效，人数轴同一池内单调。** `poker_ocr/ranges.py:380-386` 把
   `_vs_<开池位置>` 丢掉了，所以「按位置分桶」在现状代码里是零效果；要让它生效必须
   重估 6 张表（IP/OOP × EP/MP/LP）。而人数轴的 2 人池档**就是现状表本身**，新增的
   只有「删什么」这一个自由度。
2. **位置轴在同一池内是恒定的，人数轴是递增的。** 一个 4 人池里第 1、2、3 家冷跟，
   位置分桶给它们的档可能完全相同（见 §4.2 反例 A），而它们面对的范围集大小差 2 家。
   `ranges.get()` 现在对三家返回同一个对象——**这不是精度不够，是表达力不够**。
   票面要修的是「第 2、第 3 个跟注者」，这是**顺序/人数**语义，位置轴天生表达不了。
3. **人数维度已经被代码承认过一次。** `poker_ocr/prompt/user/preflop.py:170` 的
   `multiway = bool(callers or limpers or behind)` 与 `:224` 的 BB 切表，是这个方向
   已经落地的二值版本。本草案只是把它从 0/1 扩到 3 档、从 BB 一个座位扩到所有冷跟座位，
   **不是新引入一个维度**。

### 4.2 位置分桶会给出错误先验的三个反例

**反例 A：同一池内位置轴恒等，人数轴才单调。**
本地真实点 `Js Ah` / `5h 6c 4c`：翻前一家开池、三家冷跟（`midL` / `upL` / `topL`，
`field_ranges` 给三家都是 `COLD_CALL_IP_vs_EP`）。位置分桶里三家都是「IP、面对 EP 开池」，
拿到的是**同一个 20.21%**；而实际第 3 家面对的是「开池者 + 2 个跟注者」的范围。
人数轴给 15.08% / 11.31% / 11.31%，至少方向是对的（越往后越紧）。位置轴在这类点上
连方向都不对。

**反例 B：两轴在同一座位上给出相反的相对顺序。**
BTN 冷跟 CO 开池（3 人池）：位置轴看「IP + 开池者在 LP」→ 设计文档最宽档 18–28%，
现状 20.21% 已经贴着上界；但池里 3 人，人数轴要求 15.08%。
反向场景：弃到 BTN、BTN 冷跟 UTG 开池（2 人池）：位置轴看「IP + 开池者在 EP」→
设计文档最紧档 10–15%，可 2 人池按票 #78 的验收**必须保持 20.21%**。
两个轴的排序在这两个场景里相反，而票面明确要修的是「人多却按最宽档」这一侧——
先修人数轴，位置轴留给后续（§7）。

**反例 C：位置轴今天没有数据预算。**
本地唯一带位置的冷跟证据是 `docs/摊牌反核-2026-11-05.md` 的 18 手摊牌：
`COLD_CALL_IP_vs_EP` 8、`COLD_CALL_OOP_vs_LP` 4、`COLD_CALL_OOP_vs_EP` 3、
`COLD_CALL_OOP_vs_MP` 3。摊到 6 张位置表 = 3 手/格；而且那批样本**没记入池人数**，
无法把「位置效应」与「人数效应」分开——用它们估位置表，等于把两个变量混在一个回归里。
人数轴的 2 人池档不需要新数据（现状就是），3/4 档只需要「删什么」的判断力，不需要
每格一个宽度。

### 4.3 诚实地说：位置轴仍然是缺口

本草案**不解**决「BTN 冷跟 UTG 开池 vs BTN 冷跟 CO 开池同宽」这个问题——
2 人池锁死不变是票 #78 的验收要求，所以它必然留着。这是有意取舍，登记在 §7。

## 5. 风险与反例

### 5.1 顺带查出的漂移：现状表的「加宽」只落地了一部分

先摆事实。2026-11-05 的摊牌反核把 `COLD_CALL_IP` 从 11.2% 加宽到 20.2%，理由写得很
直白：「摊牌见过 JJ/AQs/**KTo**/**98o** 冷跟，旧口径是 TAG 假设」；
`poker_ocr/ranges.py:257-258` 的注释也说「非同花加 K9o+/Q9o+/J9o+/T9o/98o/87o」。

**但实际 token 里没有这些手。** 实测 `expand_tokens(ranges._RULE_TOKENS["COLD_CALL_IP"])`：

| 注释 / 校准文档声称加了 | 实测在表里 |
|---|---|
| `K9o+`（K9o/KTo/KJo/KQo） | 只有 **KJo / KQo**（`KTo`、`K9o` 都不在） |
| `Q9o+`（Q9o/QTo/QJo） | 只有 **QJo**（`QTo` 不在） |
| `J9o+` / `T9o` | **JTo / T9o** 在 |
| `98o` / `87o` | **都不在** |
| 一/二隔张 `97s/86s/75s/64s/53s`（`ranges.py:257`） | `97s / 86s / 75s` 在；**`64s` / `53s` 都不在**（表里有 `54s`，但那是另一手牌） |

OOP 更少：非同花只有 `KQo / KJo / QJo`，连 `JTo / T9o` 都没有。
`expand_tokens(["K9o+"])` 本身能正确展开出 4 个键，所以不是语法问题——
是加宽时 token 列表没写全。

两个后果：

1. **摊牌反核点名的证据（KTo / 98o）从来没被兑现。** 加宽只落了同花部分
   （`K7s+` / `Q7s+` / `J7s+` / `T7s+` 确实加了）与非同花的一部分，`64s / 53s` 也没落地。
   这本身是票 #79（现状与缺口）该收的事实，本文只记录、不修。
2. **所以草案与实测的冲突面比表面窄。** 草案 tier3 删的 IP 手牌是
   `K7s–K9s / Q7s–Q9s / J7s–J8s / T7s–T8s / QJo / JTo`，tier4 再删
   `97s / 86s / 75s / KJo`——**全是现状表里确实有的手牌**，不是「删掉摊牌见过的牌」。
   唯一擦边的是 `JTo`：现状表里最弱的一张非同花宽张，也是 3 人池里最该被统治的牌。

真正的风险仍然是这个：2026-11-05 的方向是「往宽」，草案的方向是「人多往紧」。两者
不冲突的前提只有一个——那 18 手冷跟摊牌**大多发生在 2 人池**。而
`docs/摊牌反核-2026-11-05.md` 不记入池人数，无法核实。这是本草案**最大的证据缺口**，
缓解办法见 §7 的最小可行取样方案。在此之前，1–2 档的温和收紧（IP 每档 −5.13/−3.77pp）
是能承受的上限；再狠就不是「按人数分桶」，而是「用均衡假设覆盖池子实测」。

§3.5 的 `Ad Jd` 三点（+9.86 / +0.19 / −1.09）就是完整机制的演示：删掉
`K9s / Q9s / J9s / 97s / 86s / 75s` 这批宽张后——
- 在 `5h 6c 4c` 这种**低牌面**上，它们只是 K/Q/J/T 高的无对子高张，A 高张赢它们，
  删掉 → 分母里被删的主要是「hero 赢的那部分」→ behind 上升（`Js Ah` +11.68）；
- 在 `5h 9d 2d 8h 4c` 这种**中牌面**上，`K9s / Q9s / J9s / 97s` 中了 9 的一对、
  `86s / 75s` 中了 8 / 5 的一对，**它们都赢 A 高张**，删掉 → behind 下降（`Ad Jd` −1.09；
  旧工具按 3 人池算是 −7.68，档位修正后只剩零头）。

同一个座位、同一条线，flop 与 river 的差值方向相反，靠的就是这条「被删的手在**这个**
牌面上算不算领先」。所以「先验收紧 = 更保守」是错的直觉，任何「分桶后一律抬高门槛」
的接入方式都会在一类牌面上反向。**接入时必须按牌面/牌力档回归，不能只看全局均值。**

### 5.2 方向不单调，而且不能靠直觉数

§3.5 的 `Ad Jd` 三点（+9.86 / +0.19 / −1.09）仍然不同号，但幅度已经和旧文
（+7.44 / −5.15 / −7.68）完全不同——**旧文的「翻号」有相当一部分是档位自计数 bug**：
`lowR` 被判成 3 人池，实际是 4 人池，turn/river 拿了比真实情况宽的先验。修正后
turn/river 的两臂几乎重合（按 `combo_weights` 加权枚举：57.00%→56.90% /
58.00%→56.98%；MC 是 56.80→56.99 / 58.06→56.97），cross-street 的方向变化仍然存在，
但不再是「翻号」量级。

机制本身没变，只是幅度更小：删掉的是
`K7s–K9s / Q7s–Q9s / J7s–J8s / T7s–T8s / QJo / JTo` 这批宽张。在 `5h 9d 2d` 上，
其中只有 `K9s / Q9s / J9s` 中了 9 的一对，其余十几张都是 K/Q/J/T 高的无对子——
**hero 用 `Ad Jd` 的 A 高张赢它们**。删一批「hero 赢的 combo」，剩下的范围里
「压过 hero」的占比自然上升：`5h 9d 2d` 上 IP 从 43.58%（t2）升到 55.28%（t4）、
OOP 从 45.60%（t2）升到 53.33%（t4，已排 hero+board 死牌，见 §5.3 的口径）。
这就是 flop 那 +9.86 的主要来源。

它解释不了 turn/river 的微负号，而且**逐手数 combo 一定会算错**：公共牌会阻挡 combo
（`9d` 在牌面上，`K9s` 只剩 `9sKs` 一个 combo，权重从 4 掉到 1），所以「被删的这批
平均比整体强还是弱」每一条街都要重算。到 `5h 9d 2d 8h 4c`，这条线已经过了两轮
check-call 事件收窄，残留范围集中在中档成牌，被删的 `K9s / Q9s / J9s / 97s / 86s / 75s`
恰好就在这一档里，删掉它们，事件后的分布往更弱处塌，behind 降 1.09pp（旧工具在
t3 下是 −7.68，把档位修正后这个效应只剩零头）。

→ 结论既不是「收紧 = 更保守」，也不是「收紧 = 更松」，而是**方向随牌面与构建路径变，
必须枚举**。§5.3 的逐座位表把「变化发生在哪一步」拆开了。任何「分桶后一律抬高门槛」
的接入方式都会在一类牌面上反向，接入时必须按牌面/牌力档回归，不能只看全局均值。

### 5.3 两条构建路径都随先验移动：`board_range` 与 `range_flow`

先纠正一个容易踩的误解：**事件模型只参与一部分点**。39 个冷跟座位里，
走 `range_flow.build_range` 收窄的有 **11** 个（全部在 turn/river：turn 7 + river 4），
走 `board_range.build` 按牌面条件化的有 **28** 个（26 个翻牌座位全是这一条，
turn/river 各有 1 个因 `spec.events` 为空也落到这里）。翻牌点的 `spec.events`
为空的直接原因是：`field_ranges` 不把翻前动作当事件。

两条路径都会让「压过我」的比例随先验变化，但机制不同。逐个座位枚举
（不抽样，按 `combo_weights` 加权，与 `_monte_carlo` 的抽样分布一致，并排除 hero+board
死牌——所以 n 比旧表小，旧表未排死牌）：

| 点 | 座位（档） | 路径 | 现状 n / P(beat) | 分桶 n / P(beat) |
|---|---|---|---|---|
| `Ad Jd` flop `5h 9d 2d` | lowL（IP, t4） | `board_range` | 218 / 43.58% | 123 / **55.28%** |
| | lowR（OOP, t4） | `board_range` | 182 / 45.60% | 105 / **53.33%** |
| | 合成 behind_any | | 69.31% | 79.13% |
| `Ad Jd` turn `5h 9d 2d 8h` | lowR（OOP, t4） | `evt` | 171 / 57.00% | 100 / 56.90% |
| `Ad Jd` river `…8h 4c` | lowR（OOP, t4） | `evt` | 166 / 58.00% | 95 / **56.98%** |
| `Js Ah` flop `5h 6c 4c` | midL（IP, t3） | `board_range` | 220 / 34.09% | 161 / **46.58%** |
| | upL（IP, t4） | `board_range` | 220 / 34.09% | 120 / **55.00%** |

| | 合成 behind_any | | 71.37% | 84.16% |

（「合成」是独立近似 `1-∏(1-p_i)`，用来对照 MC：`Ad Jd` flop 69.31 vs MC 70.39、
turn 57.00 vs 57.40、river 58.00 vs 58.06、`Js Ah` 71.37 vs 73.91——差 ≤2.5pp；
`4d Ad` 的合成 20.88/24.33 比 MC 34.45/36.85 低，因为 MC 还要对 1 家未建模对手
按随机牌补位（players=4、冷跟座位 2），枚举没有这一项。§3 的正式数字仍以 MC 为准。）

两条读法：

1. **`evt` 路径（turn/river）不是「先验窄了 behind 就窄」**：river 先验从 16.74% 收到
   9.65%（−7.09pp），事件收窄后的 P(beat) 只从 58.00% 掉到 56.98%（−1.02pp）。
   旧文在 t3 下看到的是 58.00%→50.45%（−7.55pp）——档位修正后这个「方向反转」基本消失。
   原因：`facing_probs`（`poker_ocr/tables/range_flow.json`）按**成牌档**
   （nut/strong/medium/weak/draw）乘性重加权，先验的档位构成一变，重加权后的分布
   跟着变。而 `poker_ocr/ranges.py` 的 `Range` docstring 明写这个耦合是**有意校准**：
   「先验范围上的平均弃牌率应该等于历史观测值」。
2. **`board_range` 路径（全部翻牌点）在本批数据上几乎是恒等映射**：`combo_count` 不变、
   枚举出来的 P(beat) 与原始先验逐位一致（`4d Ad` / `Ah Jc 3d` 上 OOP t2 = 11.05%、
   t3 = 14.93%，就是 `ranges.get(prior_id)` 与 `ranges.get(..._n3)` 直接数出来的值）。
   所以**翻牌点的差值完全来自先验构成本身**，不是牌面条件化另加的东西——`4d Ad` /
   `Ah Jc 3d` 上 OOP t3 只删了 47 个 combo（181→134），P(beat) 就动了 3.88pp。
   它仍然与先验耦合，但耦合点在别处：`poker_ocr/ranges.py:142-145` 的
   `Range.prior_id` 注释写「条件弃牌率要用它做绝对水平的校准：先验范围上的平均弃牌率
   应该等于历史观测值」——牌面条件化拿先验当锚，锚一换，条件弃牌率跟着换。

→ **换冷跟先验会同时移动两条路径的校准点。** 票 #78 接入后不能只核对宽度表，
至少要①重跑一次摊牌反核（`docs/摊牌反核-2026-11-05.md` 的方法），
②重跑本工具对比新表 vs 草案表的 behind 分布，确认没有把 `range_flow` 的
`facing_probs` 校准推离观测值。

### 5.4 桶边界跳变

IP 档间跳变 −5.13pp / −3.77pp，OOP −3.92pp / −3.17pp。一个溜入者被误识别成
「没有」或「有」，先验立刻跳 3–5pp，而且是在**没有任何牌面信息**的翻前。
缓解（写进 §6.4）：只在动作顺序里**明确看到** `call` 时升档；看不到就退现状档，
不做「按在局人数猜」。

### 5.5 样本稀疏，OOP 4 人池只有一手牌

12 个可引用的受影响点里，tier4 占 6 个；`COLD_CALL_OOP_n4` 本批有 **3 个座位观测**，
但全部来自 `Ad Jd` 同一手牌的 flop/turn/river——同一个座位的三次快照，不是三次独立
跟注。也就是说 OOP 4 人池那一档（128 combos / 9.65%）的实测证据仍然只有一手牌，
评审时对它的把握应该低于 IP_n4（5 个座位、跨 3 手牌）。

### 5.6 会推着建议变紧

本次有 **1 个点跨越** `_BEHIND_DEMOTE = 0.35` 这条线：`4d Ad` / `Ah Jc 3d`
35.08% → 37.87%，`big`/`very_big` 档的价值成牌会降一档，建议随之变紧。
这是「分桶会改变建议」的第一个实证。是否可接受只能由维护者在 ab 测试集上判断
（agent 不跑 A/B，见 §7）。

## 6. 给票 #78 的接入建议

### 6.2 键长什么样

保持现有形状，在末尾加人数后缀（本节是草案期建议；#78 实际落地的版本见 §6.6，形状一致）：

- 无后缀 = 2 人池 = 现状；
- `_n3` / `_n4` = 3 / 4+ 人池；

```python
if upper.startswith("COLD_CALL_"):

    base_head = head.split("_VS_", 1)[0]
    ip_oop = base_head.replace("COLD_CALL_", "", 1).strip("_")
```

### 6.4 缺档怎么退化：退「现状单桶」，**不要退「范围未知」**

这是本草案最重要的一条接入约束。

如果入池人数不可知（翻前动作顺序缺失、溜入未被识别、座位不明），**必须**退到
无后缀的 `COLD_CALL_*`（= 2 人池 = 现状），而不是让该对手变成「没有先验」。

理由：`field_ranges` 给不出 prior 时，该对手会掉出建模集，落进
`hand_vs_ranges._monte_carlo` 的 `random_opponents`（均匀随机牌）。均匀随机牌比任何
冷跟范围都**宽**，`behind_any` 会系统性偏低——正好是票面要修的方向的反方向。
「不知道几个人进池」≠「他没有范围」。修前工具用「当前在局人数」反推档位，在
`Js Ah` 这类点上多算一家、给出过 +16.63pp 的虚高差值（§6.7）；接入时不要重复
这个错误。

### 6.7 修复记录（#78 评审，2026-11-19）

评审发现 `tier_for_seat` 把「该座位自己更早那次跟注」也算成了另一个已入池的人：

```python
# 修前：n_way = 1 + index + 1，index 是该座位最后一次 call 在 order 里的下标
# 修后：n_way = 1 + len(set(order[:index]) - {key}) + 1
```

典型场景：SB 先补齐 0.5、再加注后再跟——第二次 call 的 `order` 里还留着 SB 自己的
第一次 call，人数多算 1，2 人池被错升 3 人池。修复后档位只数**别的**座位（去重）加
开池者与自己，与 §2.1 的定义一致。同时把报告工具里自抄的一套档位映射删掉、改为直接
调生产 `preflop_entry_order` / `tier_for_seat`，所以本次是第一次「测量口径 = 生产口径」。

| 最大档 = 3 人池 | 8 点 / −0.90 | 6 点 / +1.12 | 点数 −2 |
| 最大档 = 4 人池 | 5 点 / +6.16 | 7 点 / +3.63 | 点数 +2 |

逐点最大的两处：`Js Ah`/`5h 6c 4c` +16.63 → **+11.68**（`topL` 从 4 档退到 2 档）、
