# 摊牌字段缺口：现有记录够不够判「牌型族 × 局面」（2026-11-13）

> 对应 GitHub issue #11（wayfinder:research，父图 #10）。
> 问题：把「摊牌亮出的具体手牌」做成**牌型族（≈10 族）× 局面键**的对手漏洞
> 证据，每手实时增量；现有 `shows` / `streets` / `seat_meta` 等字段够不够？
> 工具：`tools/showdown_field_audit.py`（只读，可复跑）。
> **一句话结论：族与局面全部可从现有记录推导，不需要新增 OCR；真正的缺口是
> winner（只有 64.7% 可推导）和亮牌归属（20.5% 的亮牌落在已弃牌座位上）。
> 事件级 witness 能产出，按人×族×局面的统计频率目前撑不起来。**

## 1 方法

- 语料：`data/hand_outbox/{pending,sent,discarded}/*.json`，共 **970 手**
  （pending 188 / sent 781 / discarded 1），schema 全为 `hand.v2`，`uid` 无重复。
- 全部数字由 `nv tools/showdown_field_audit.py` 现场统计；「覆盖率」= 键存在且
  值非 None/空列表/空字符串/空 dict。
- 三个口径分开报，避免混用：
  1. **`_showdown` 口径**（`poker_ocr/opponent_profile.py:602`）：2 张亮牌 +
     牌面 ≥3 即收，不看亮牌人是否已弃牌；
  2. **clean 口径**（本笔记推荐）：在上面基础上加「该座位最后动作不是 fold」
     且「仍在最后一条街的 `street_active` 里」；
  3. **showdown 手**：牌面 5 张 + 河牌起始 ≥2 人（真正走到摊牌的手）。
- 对照源码：`_showdown`（:602）、`_seat_meta`（:386）、`_bet_size_ratios`
  （:573）、`observations_from_hand`（:660）、`hand_track.record_shows`
  （`poker_ocr/hand_track.py:657`）、落库 `out["shows"]`（:2290-2296）、
  `street_active`（:2249-2259）、`live.py` 的 `partial` 与 `_write_hand`
  （`poker_ocr/live.py:2076-2081`、:2587）。

| 字段 | `_showdown`（:602） | `observations_from_hand`（:660） |
|---|---|---|

| `shows[].cards` | ✅ 要求恰好 2 张 | ✅ 同上 |
| `shows[].name` | ❌ | ❌（名字走 seat_meta） |
| `shows[].position` | ❌ | ❌ |
| `board` | ✅ 要求 ≥3 张 | ✅ |
| `streets[].street/actions[]` | ✅ 只看翻后 bet/raise 判 `aggressive` | ✅ 全部线路统计 |
| `street_active` | ❌ | ✅ 补推弃牌、判断在局 |
| `seat_meta.position` | ❌ | ✅ limp 的 BB 判定、位置排序 |
| `start_stacks` | ❌ | ✅ 旧记录推断「被发过牌」 |

## 3 判族需要什么

| 需求 | 需要的字段 | 现有记录 | 判定 |
|---|---|---|---|
| **判牌型族** | `shows[].cards`（2 张）+ `board`（≥3） | 2 张手牌 308 手，其中牌面 ≥3 的 304 手 | **能推导**（`coach.evaluate` / `range_flow.hand_class`）；但 `_showdown` 不落 cards，要加字段 |
| **判街** | `streets[].street` + 动作顺序 | 100%（4 条街齐全） | **有**；注意 `shows` 自身没有街别 |
| **面对下注 vs 主动** | 同街前序 `bet/raise`、`all_in` | 100%（60% 动作是 inferred，需带置信标记） | **能推导**；`aggressive_showdown` 已这么做 |
| **判位置** | `seat_meta[].position` | 97.3% 非空 | **有**；2.7% 退化到 `unknown` |
| **判多人池** | `street_active[street]` / `players_dealt` | 100% | **能推导**；`street_active` 是**街初**集合，不是街末（G9） |
| **判牌面纹理** | `board` | 翻牌 804 手 | **能推导**（花色同异、对子、连张、高张） |
| **判亮牌是否赢家** | 无 winner / pot award 字段 | 无 | **必须补采或推导**：385 手摊牌里只有 249 手（64.7%）可推 |
| **判摊牌 vs 提前亮** | 无 show 街别 | 无 | **能推导（弱）**：最终牌面 <5 张 = 提前亮（71 手），但无法区分「截断」 |
| **判玩家身份** | 无平台 ID | `name` + `table_signature` + `table_roster` | **能推导（弱）**：改名/同桌同名不可靠（G6） |

族的具体切分（9 类还是把「一对」拆成强弱两档凑 10 族）是 spec 决策，不是数据
问题：`coach.evaluate` 给 9 类，`range_flow.hand_class` 还能给
nut/strong/medium/weak/air 与听牌档，两者都只需要 cards+board。

## 4 缺口清单

### G1 winner 缺失（§8.5 同一条）

- **缺什么**：`shows` 只有牌，没有「谁赢了 / 谁收池」。
- **影响**：能回答「他摊牌时有什么牌」，不能回答「他赢的时候 / 输的时候亮什么」；
  亮牌样本天然偏向赢家（输家可以 muck），没有 winner 就无法校正这个选择偏差。
- **补采成本**：高——要 OCR 收池动画/筹码飞向，属新识别能力（设计文档 §8.5 已
  判定不进首批）。
- **退化方案**：写 `winner_derived` 而不写 `winner`：按「河牌起始在局 − 河牌
  弃牌」得到候选集，对亮出的手牌排序取最大。实测覆盖 249/385；其中 110 手只有
  1 人亮牌，这个「赢家」实际是「唯一亮牌者」，漏拍一次就会把输家当赢家。
  没有 active 亮牌的 136 手（其中 129 手完全没亮）只能记 `winner=unknown`。

### G2 亮牌没有街别 / 时机

- **缺什么**：`shows[]` 没有 `street`、帧号或时间戳，无法区分摊牌亮与提前亮，也
  无法判断这次亮牌属于哪一手（见 G3）。
- **影响**：摊牌样本与「主动秀牌」样本混在一起；后者是玩家自选，选择偏差更大。
- **补采成本**：低——落库时把 `hand.street` 或帧号一起写进 show 即可（纯代码，
  不需新 OCR）。
- **退化方案**：用最终牌面长度推：5 张 = 摊牌，<5 张 = 提前亮/截断（71 手）。

### G3 亮牌归属污染（最大的数据质量缺口）

- **缺什么**：没有把一次亮牌绑定到「哪一手、哪一街、哪一帧」的稳定锚点。
- **实测**：616 条亮牌里 **126 条（20.5%）** 的座位在本手的最后动作是 `fold`，
  涉及 **105/356 = 29.5%** 的亮牌手牌；这 126 条的 fold **全部是 inferred**。
  其中 64 条 fold 发生在翻前（此后再无动作），40 条与 `street_active` 自相矛盾
  （人还在最后街的活跃集合里，却有一条推断弃牌）。
  例：`data/hand_outbox/sent/20261030-0c2ec0fc88.json` 里 midR/upL 翻前被推断
  弃牌，却各亮两张 77/33；`data/hand_outbox/pending/20261111-e788859bf8.json`
  里 upR 翻前弃牌却亮了 1 张（1 张只可能是河牌主动秀）。
- **影响**：直接用 `_showdown` 的口径会把已弃牌的人算成摊牌者，族分布和
  aggressive 标记同时被污染；这是本需求**唯一必须加闸门**的地方。
- **补采成本**：低（消费侧过滤）；根治要修 `_target_hand`
  （`poker_ocr/hand_track.py:745-756`）——当前只要新手牌已经有 hero_cards，
  上一手残留的亮牌就会挂到新手牌上；`_active_shows` 只防重复，不防挂错手。
- **退化方案**：clean 闸门（最后动作非 fold + 在最后街 active 里），丢弃
  64+9 条；剩余 453 条 / 280 手 / 86 人。丢了约 13% 的样本，但换来可解释性。

### G4 单张亮牌 86 条判不了族

- **缺什么**：只有 1 张牌。
- **影响**：判不了牌型族（不知道另一张），但可做范围排除（例如没 A 就不是 AA）。
- **补采成本**：0（数据已在），只是 `_showdown` 丢弃。
- **退化方案**：不纳入族统计；如果要纳入 `showdown.any` 频次，单独计数并注明
  「1 张」——不能与双张摊牌混算族。

### G5 具体牌根本没落库

- **缺什么**：`HandObservation` 只有 `showdown_category: int|None`（0–8），
  没有 `cards`，也没有牌面纹理/赢家。
- **影响**：现有画像只能统计「弱摊牌率」，无法按族、按局面拆。
- **补采成本**：**最低**——纯代码：`_showdown` 多返回 cards + 街别，
  `HandObservation` 加 `showdown_cards` / `showdown_street`（设计文档 §7.1 已列）。
- **退化方案**：不补就只能继续用 9 档 category，做不了族×局面。

### G6 玩家身份只有名字

- **缺什么**：没有平台玩家 ID；`opponent_key` 就是 normalize 后的 name
  （`poker_ocr/opponent_profile.py:715-716`）。
- **影响**：跨场次累积会把同名不同人合并、把改名的人拆开；witness 是「按人累积」
  的产品，这个键直接决定证据归属。
- **补采成本**：高（UI 通常不显示 ID）；可做的是 `name + table_signature`
  圈定同场次，跨场次靠人工 alias。
- **退化方案**：只在同一 `table_signature` 内累积；跨桌不合并，宁可少算。

### G7 `pot_start` 缺失 5–14%

- **影响**：底池赔率、下注尺度（1/3、2/3、超池）这类局面键在该街不可算。
- **补采成本**：0（已有字段，缺的是识别稳定性）。
- **退化方案**：该街的尺度键标 `unknown`，只保留「面对下注 / 主动」这层。

### G8 `partial` 字段实际不存在

- **实测**：`live.py:2587` 会写 `record["partial"]=True`，但 970 条记录里
  **0 条**带这个键（`data_quality.status` 也没有 `partial`）——只在进程正常
  退出的 final flush 才写，实际没落下来。
- **影响**：`observations_from_hand` 里三处 `not hand.get("partial")`
  （:812/:891/:920）的「截断手不补推弃牌」闸门恒为真，等于没有。
- **补采成本**：低（改落库时机或改用 `data_quality.status`）。
- **退化方案**：与 G3 共用消费侧闸门；不要依赖 `partial`。

### G9 `street_active` 是街初集合

- **实测**：`street_active` 取 `street_start_active`（`hand_track.py:2249-2259`），
  是每条街**开始**时在局的人。
- **影响**：拿它判「最后在局」会多算本街弃牌的人；赢家推导必须先减去该街 fold。
- **补采成本**：0（动作线可校正）。
- **退化方案**：脚本已按「街初集合 + 该街 fold」校正。

## 5 与 §8 四个前置 bug 的关系

| §8 bug | 对本需求 | 理由 |
|---|---|---|
| 8.1 BB walk 被算成开池机会 | **无关（字段层）；只在用机会型分母时相关** | witness 挂在真实下注动作上，walk 没有任何动作，自然不会产出 witness。但若拿 `open_opp` 当 `preflop.unopened` 的分母，walk 会稀释开池率——那是统计口径 bug，不是字段缺口。 |
| 8.2 iso-raise 未采集 | **无关，可现算** | `streets` 的 preflop 序列完整（call/raise 顺序都在），facing_limp / iso_raise 只是派生字段；`HandObservation` 没有它，但原始记录够。 |
| 8.3 单张亮牌被整体丢弃 | **部分相关** | 单张判不了族，所以对「族」不是阻塞；它只让 `showdown.any` 频次偏低（86 条/46 手）。把单张纳入摊牌计数可以，但**不能进族统计**。 |
| 8.4 bet_sizes 无街维度 | **无关（数据层），是派生结构问题** | `streets[].pot_start` + `amount` 已按街存在，`_bet_size_ratios`（:573）也是按街算完再拍平；要修的是 `HandObservation` 的结构。真正的数据缺口是 5–14% 的 `pot_start` 缺失（G7）。 |

结论：**四个 bug 没有一个是本需求的字段阻塞项**。8.3 与「摊牌频次」有关，8.1
与「机会型分母」有关；族×局面本身只依赖 `shows.cards` + `streets` + `board` +
`seat_meta`，这些都在。

## 6 样本量：witness 到底能不能撑起来

clean 口径（G3 闸门后）：

- **453 条**亮牌 / **280 手** / **86 名玩家**；
- 每人摊牌数：1 次 28 人、2 次 9、3 次 8、4 次 10、5 次 4、6 次 1、7 次 4、
  8 次 3、9 次 2、10 次 3、11–28 次共 12 人；**≥8 次 22 人、≥10 次 17 人**；
- 族分布：两对 147、一对 147、高牌 40、顺子 37、同花 30、三条 28、葫芦 21、
  同花顺 2、四条 1；
- 单族格（同一玩家同一族）≥3 次的 **24 人**，≥5 次的 **4 人**，≥8 次的 **0 人**；
  族×主动/被动格同理（24/4/0）。

对照设计文档 §5.3 的 `measured / shrunk / insufficient` 三级：按人×族×局面，
绝大多数格连 `insufficient` 都到不了。**事件级 witness 可以产出（每手一条
`(uid, opponent, family, spot, street, position, players, texture, winner?)`），
但按人按族按局面的频率结论，现有 970 手不够。**

winner 的覆盖率再打折：385 手摊牌里 249 手可推（64.7%），110 手是「唯一亮牌
者」（漏拍即错），136 手完全推不了。所以 winner 只能作为 `derived` 证据，
不能当 `measured`。

## 7 结论

1. **族与局面字段全部可推导，不需要新增 OCR**：cards（2 张）+ board（≥3）判族，
   streets 判街/面对下注/主动，seat_meta 判位置，street_active 判多人池，board
   判纹理。304/308 的二手亮牌手牌可判族。
2. **唯一真正的字段缺口是 winner**；其次是亮牌归属（G3）——后者不是「缺字段」，
   而是现有字段的绑定不可靠，必须先加消费侧闸门，否则 20.5% 的亮牌会污染统计。
3. **§8 四 bug 都不是阻塞项**：8.1/8.2/8.4 与字段无关（8.2/8.4 甚至可现算），
   8.3 只影响摊牌频次、不影响族。
4. **最小改动顺序**：① `_showdown` 多返回/落库 `showdown_cards` +
   `showdown_street`；② 消费侧 clean 闸门 + 丢弃原因；③ winner 先写
   `winner_derived`（带 confidence），不冒充 measured；④ 身份键限定在
   `table_signature` 内；⑤ 修 `partial`（或删掉这个闸门）。
5. **一句话判断**：**不补采、只用现有数据，能撑起「族 × 局面」的 witness
   事件流（覆盖 280 手 / 86 人，除 winner 外字段可推导率接近 100%），但撑不起
   按人×族×局面的可信频率；winner 与亮牌归属是两个必须先解决的闸门。**

## 8 复跑方式

```bash
# 全量（默认读 pending/sent/discarded）
nv tools/showdown_field_audit.py

# 只看 sent，或输出机器可读 JSON
nv tools/showdown_field_audit.py --hands 'data/hand_outbox/sent/*.json'
nv tools/showdown_field_audit.py --json > /tmp/showdown-audit.json
```

脚本输出九段：语料 / 顶层覆盖率 / shows / streets / seat_meta / board /
hero_cards / advices / `_showdown` 复算 / 可推导性 / witness 样本量。
`--json` 里 `contract` 段记录了 `_showdown` 与 `observations_from_hand` 的
取用清单，改口径时同步。
