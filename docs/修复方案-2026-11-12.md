## A. 滑杆容错（先做，零代码也能落一半）

### A1. 配置（`config/bet_slider_mac.json`）

```diff
-  "total_timeout_ms": 8000,
+  "total_timeout_ms": 6000,
-  "max_steps": 80,
+  "max_steps": 6,
   "accept_ratio": 0.0,                      # 低侧：绝不落得比建议小
+  "accept_overshoot_ratio": 0.05,           # 高侧：最多 +5%
+  "accept_overshoot_min_bb": 1.0,           # 5% 不足 1BB 时按 1BB 算
```

**近似落注只许「多」不许「少」**（2026-11-13 用户确认）：区间 =
`[target, max(target*1.05, target+1BB)]`，上限再按 `round_to_bb` 向上取整。
27BB 的 3-bet → 27*1.05 = 28.35，0.35 不足 1BB 按 1BB 算 → **27–29BB 都算到位**；
10BB → 10–11BB；100BB → 100–105BB。26BB 不在区间里（比建议小 = 自己降尺度）。

`_drag_curve_note` / `_total_timeout_note` 同步改写，说明「本机 profile 允许近似落注，
其它 profile 默认仍是 0」。

- 为什么 0.05 不是 0.02：27BB 的 ±1 落在 3.7%，0.02 不够；0.05 在 27BB 上等于 ±1.35
  （26/28 都进），在 2BB 上等于 ±0.1（等于没开，低额仍按整数网格精确落）。
- **总超时不能压到 2.5s**：今天滑杆「打开 + 确认」本身就要 **~2.1s**（`drags=0` 的
  记录是 2065/2122/2124ms），每多拖一步再 +0.93s（2 步 3.96s、3 步 4.9s）。压到 2500
  等于绝大多数 bet 直接超时。收到 **6000 + 步数 6** 的实际效果是：正常 2–4s 落注，
  最坏 ~5.8s 收口（今天是 8s 上限却一路拖到 9.04s）；超时那一刻若额度已经在允许
  区间，就按它落注（软截止），不再「明明能下却超时丢弃」。
- **不会**出现「一进 5% 就停」的系统性少下注：`bet_slider.py:1477` 的 `approx_ok`
  要求 `best_error` 和当前值都落在区间内，只接受「最近可达」；27BB 的平局会落在
  26 或 28（≤3.7%），日志写 `accepted_approx`，事后可逐条对账。
- 想让「点击不挡路」不是靠压超时——那是 C 的事。压超时只负责「别把整个回合耗光」。

### A2. 代码：振荡判据要认得「两个相邻值」

现状 `bet_slider.py:1460-1470` 要求最近 4 步严格 `A,B,A,B`，今天的
`28,26,26,28,28,26,26` 永远不命中，于是拖到超时。改成：

```python
tail = recent[-3:]
if (len(tail) == 3 and len(set(tail)) == 2
        and abs(amount - target) > self.settings.tolerance_bb):
    gap = abs(max(tail) - min(tail))              # 客户端在该区间的粒度
    if gap <= max(1.0, target * 0.1):
        # 已尽力、只在两个相邻刻度之间：交给后面的 approx_ok / 报错
        break
```

配套：把观测到的 `gap` 写进 `result.evidence["observed_step_bb"]`，以后调参不用猜。

### A3. 代码：落注前连读两次（防 7→6/8 误读）

今天到达过的额度里 1–11 的奇偶数都出现过，只有 26/28 反复、27 一次没有——既可能是
客户端在这段是 2BB 步进，也可能是气泡把 `27` 读成 `26/28`。两者用同一个办法消除歧义：
**只在「读到值与目标差 ≤ 1 个观测粒度」时才重读一次，两次一致才认**（成本 ~150ms，
其余情况不加开销）。不一致就取 `min`（保守），并记 `amount_read_flaky`。

## B. 筹码图标 → 下注阻断

目标：**能读对就读对；读不对就降级，不丢整帧**。

### B1. 解析容错（`poker_ocr/parse.py`）

现有两条正则只允许「单位后是非数字噪声（≤3 个）」或「单位后是 0/O（≤2 个）」，
所以 `1BB8`、`5.5BB◎8` 会被判 `不是金额形状`。加第三条：**认到单位为止，尾巴 ≤2 字
一律当噪声**，但必须已经有完整金额 + 单位：

```python
# 单位之后最多 2 个字（筹码图标/光圈/误读的 8）当噪声；前面仍要求数字+单位。
_AMOUNT_CUT_AT_UNIT_RE = re.compile(r"^[^0-9]*(\d+(?:\.\d+)?)\s*(BB|B)")

m = _AMOUNT_CUT_AT_UNIT_RE.match(t)
if m and len(t) - m.end() <= 2:
    return Amount(t, float(m.group(1)), m.group(2).upper(),
                  tail_noise=t[m.end():])
```

`Amount` 加 `tail_noise: str | None`，`to_debug()` 带上——这样「有多少帧是靠裁尾巴读出来的」
可以直接统计，不会变成第二个静默口径。

> 只裁尾巴，**不动**前导融合（`C6BB` 已经被 `^[^0-9]*` 覆盖；`6.5 → 26.5` 属于前导
> 数字融合，见 B3）。

### B2. part 级重试（`roi_reader.py` + `frame_state.py`）

`RoiRead.parts` 是 `[(text, score)]`，但 `frame.text()` 直接 `"".join(...)`，所以
「`1BB` + `8` 两个框」会拼成 `1BB8`。加：

```python
# RoiFrame
def parts(self, key: str, seat_id: str | None = None) -> list[tuple[str, float]]:
    ...
```

`frame_state.py:389/453` 的 bet 解析改成：

```python
bet_raw = frame.text("bet", sid)
bet_a = parse_amount(bet_raw)
if not bet_a.ok:
    for text, _score in frame.parts("bet", sid):
        cand = parse_amount(text)
        if cand.ok:
            bet_a = cand
            p.notes.append(f"bet: 多框，取金额框「{text}」")
            break
```

### B3. （**不做**）失败降级，不丢整帧

2026-11-13 用户确认：**「errors 非空 ⇒ 整帧丢弃」这条铁律不破**。所以不做
「解析失败降成 `bet_unknown` 继续跑」的例外，改成两条互不冲突的措施：

1. **数字清洗**（B1 + B2）把「本该读对却被图标带坏」的场景真正读对 ——
   阻断消失靠的是读对，不是放宽门禁。
2. **新增一条几何硬闸** `bet_gt_street:<seat>`（`frame_state.py`）：单个座位的
   下注不可能超过本街总额（`pot - pbs`）。清洗会把 `5.5BB` 读成 `55BB`，
   只要底池够大，`bet > pot` 就漏过去了；10 倍的 to_call 会同时毁掉建议和
   手牌记录，所以这里**报错丢帧**（与 `bet > pot` 的降级口径刻意不同）。

### B4. 10 倍错值的对账修复（可选，看 B1 上线后的统计）

`bet > pot` 只能兜住「比全池还大」。更强的判据是「单个座位不可能超过本街总额」：
`p.bet > street_total + 1e-6` → 降级。若要**修回**数值（`26.5 → 6.5`、`55 → 5.5`），
可以枚举候选（原值 / 去掉首位数字 / ÷10）挑「让 `sum(bets)` 与本街总额对齐」的那个；
对不上就保持 unknown。建议先只做降级，等 B1 跑一周看 `tail_noise` 与 `bet_unknown` 的量再决定。

### B5. ROI 收紧（可选，最后做）

`config/table_wpk_mac.json` 的 `seats[].bet_slot` 是归一化矩形。今天的样本显示：
左侧座位筹码在数字**前**、右侧座位筹码在数字**后**。若 B1 上线后仍偶发，再给每个座位
加可选 `bet_inset`（左右各一个比例，默认 0），在 `profile.py` 里校验范围，按座位收紧。

## C. 点击移出主循环（收益最大，改动面也最大）

### C1. 只搬鼠标，不搬安全闸

安全闸（`_click_skip_reason`、`decision_key` 比对、`_click_paused`、`confirm_click`）
**全部留在主线程**并同步执行；只有 `self.clicker.run(...)` 这一段（滑杆长按/拖动/读气泡）
交给工作线程。这样「点不点、点哪条」的判断时序完全不变，改动只有执行位置。

### C2. 先给建议，再动手（一行顺序，体感立刻变）

`live.py:1985-1999` 现在：

```python
click = self._maybe_click(...)        # ← 3–9s
data["click"] = click.to_dict()
...
self._publish("advice", dict(data))   # ← 用户这时才看到
self._log_advice(advice)
```

改成：

```python
self._publish("advice", dict(data))   # 先给结论
self._log_advice(advice)
click = self._maybe_click(...)        # 再执行
if click is not None:
    data["click"] = click.to_dict()
    self._log_click(click)
self.writer.write({...})              # 落盘顺序不变，states 契约不动
```

（异步版本里 `writer.write` 提到点击之前，点击结果另发 `click` 事件，见 C4。）

### C3. 执行器抽象：默认内联，live 用线程

新增 `poker_ocr/click_worker.py`：

```python
class ClickExecutor(Protocol):
    def submit(self, fn: Callable[[], None]) -> None: ...
    @property
    def busy(self) -> bool: ...

class InlineClickExecutor:          # 默认：测试 / 离线回放 / dry-run
    def submit(self, fn): fn()
    @property
    def busy(self): return False

class ThreadClickExecutor:          # live 启动时装配
    def __init__(self, log): ...
    # 单线程 + 队列，busy 用 threading.Event 暴露
```

`LiveProcessor` 增加 `click_executor` 参数（默认 `InlineClickExecutor`），
**现有 18 个 `test_auto_click_*` 不用改**（默认内联就是同步语义）。

### C4. 在途闸 + 新事件

- `processor.click_in_flight`：为真时主循环**跳过 OCR/决策**（不计数为丢弃、不打丢弃日志），
  每秒打一行「[点击] 滑杆执行中… Ns」心跳（照 `log_advice_wait` 的样子）。

## J. 第二轮（2026-11-13 01:0x）：小数点、即时落注、点击异步

③ 把点击移出主循环（建议到执行慢）。

### J1. 小数点：不裁点 + 吞了点就按几何修回来

- **不裁点**：清洗只裁图标（`5.5BB0` → 5.5、`c24.5BB` → 24.5），点永远在数字里。
- **吞了点就修**：`5.5BB` 被读成 `55BB` 时，靠几何不变量把它修回 5.5 ——
  `_repair_decimal(value, 本街总额)`：÷10 / ÷100 取第一个「≤ 本街总额 且落在
  0.5BB 网格上」的候选。
  - 55 在本街总额 33.5 里 → 修成 5.5，**不丢帧**；
  - 36 → 3.6 不在 0.5BB 网格上 → 说明不是丢小数点，照旧 `bet_gt_street` 丢帧。
  - 只在几何不可能（`bet > 本街总额`）时触发，正常读数一个都不会被改。

### J2. 滑杆：一进允许区间就落注

循环顶部多一条：`low <= 额度 <= high` 且不是精确命中 → 直接落注（`reason=window`），
不再等「拖到精确值 / 软截止 / 平台期」。模拟今天那手（偶数档、目标 27、起点 17）：

```

```

`total_timeout_ms` 也随之收到 5000（覆盖 3 步）。平台期 / 跨目标 / 软截止三条
兜底保留：它们只在额度**还没进区间**时才起作用（那种情况本来就该报错）。
